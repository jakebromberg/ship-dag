# Escalation policy — when to grill the human

`/ship-dag` runs autonomously *except* at six human-in-the-loop points — A (triage), B (implement/review), C (cross-repo cutover), D (retrospective and tripwires), E (rate-limit window), F (resource pressure). A and B fire when the design premise breaks — a well-specced issue Sonnet-implements and survives the Opus gate cleanly; **when that premise breaks, that break is the escalation signal.** C and D are **scheduled gates** built into the loop. E is neither: it fires when the account's five-hour rate-limit window can't be waited out cheaply (step 4's preflight, and the identical fork mid-recovery-recipe below) — an infra constraint, not a premise break, and deliberately kept distinct from B (see the *Point E* section — a rate-limit death is not a model failure). F fires at a guarded step — an engine invocation, step 6.2's CI re-run, a review/fix hand-off — when machine memory pressure is `critical` and waiting has not cleared it, or the lease stays busy (see *Point F*'s per-step table).

## Triggers (any one → pause and grill)

1. **Underspecced issue** — triage (or the implement subagent) cannot resolve an ambiguity from the issue body + repo conventions. A guess would be a coin flip on intent.
2. **Architectural fork or new dependency** — the work forces a design choice with lasting consequences, or pulls in a new third-party dependency.
3. **Unclearable blocking finding** — the Opus gate blocks the PR (a finding whose `category ∈ --block-on` **and** `verdict == CONFIRMED` **and** whose `blocking` is not explicitly `false`, or one whose category is outside the enum at all) and `/review-loop` cannot clear it within `--max-review-iter`, or it needs a design decision rather than a mechanical fix.
4. **Unreadable review, twice** — `review-gate.mjs` exits 3 (unparseable review file, no `findings` array, or a finding count disagreeing with what the Review subagent reported writing) and a re-run of the reviewer exits 3 again. One exit 3 is a re-run; two is a signal that something is wrong with the reviewer or the state dir rather than with the PR. Never fall back to merging on CI alone, and never repair the file by hand — a review nobody can read is not a review.
5. **Non-flaky CI failure** — CI fails for a real reason (not a known-flaky/infra retry). Per global rules, ≤2 manual retries on infra failure, then stop — never loop.
6. **Merge conflict needing judgment** — a rebase conflict whose resolution isn't mechanical.
7. **Oversize issue** (point A) — triage estimates the issue needs more than 200 added lines of production source. The fork is split-now vs accept-the-size, and it is a scope call the human owns. It costs minutes here and a whole branch later, so it is worth a grill even though nothing is ambiguous.
8. **Rate-limit window can't be waited out cheaply** (point E) — the step-4 preflight (`scripts/rate-limit-preflight.mjs`), or the identical fork hit mid-recovery-recipe while waiting out a live rate-limit death, finds the five-hour window at/above threshold with the reset more than `--wait-max-minutes` away, or no reset time at all: wait / defer this wave (or issue) / stop the run.
9. **Resource pressure or lease wait past its cap at a guarded step** (point F) — the resource preflight (`scripts/resource-preflight.mjs`), run before an engine invocation or a review/fix hand-off, still reads `critical` after `--wait-max-minutes` (default 15) of waiting, or step 6.2's reruns, a hand-off subagent's `lease-wait` returns or the resource route's stops for one ref pass their cap (see the table): wait / start anyway / defer this step / stop the run.
10. **Tripped tripwire or overdue review** (point D) — step 7's `telemetry.mjs tripwires` reports a `tripped` state or a `reviewOverdue` date. Answered confirm-offline, retune, or dismiss-with-reason, in a grilling of its own in step 7.
11. **A remote host cannot run its sub-wave** (step 4b) — `host-sync-claude`, `host-prepare` or `host-run` exits `3` (the host could not be reached, nothing changed or started on it), or `host-sync-claude`/`host-prepare` exits `1` (a failed sync, or drift the sync did not clear). See *A remote host that cannot run its sub-wave*.

## Protocol

`grill-me` is inherently interactive and one-question-at-a-time, and the orchestrator is *already* the interactive agent — so conduct the interview **inline** rather than spawning `grill-me` (which would hijack the turn). Steps:

1. **Batch, don't drip.** At the triage gate (HITL point A), the retrospective gate (point D) and the tripwire gate (point D, step 7), collect *all* underspecced questions and proposals across the wave and grill once, not per-item.
2. **Give full context** — the issue, the relevant diff/finding, and why the autonomous path stopped. Use `AskUserQuestion` for crisp forks (2–4 options, recommended first); use an inline grill-me-style interview for open-ended design questions.
3. **Persist the resolution** as a GitHub issue comment (ghost-writer: no Claude/AI attribution), and update the issue body if scope changed — so peers and future waves inherit the decision. A tripwire answer has no issue: it persists in `references/decisions.md` and `references/tripwires.json` instead (SKILL.md step 7).
4. **Resume the wave** with the decision applied. Only genuinely cleared issues proceed to implementation.

Suggest the user run `/grill-me` themselves if they want the full adversarial treatment on a thorny fork.

## Point D — the retrospective gate (scheduled, not premise-break)

D has two sources. The retrospective fires from step 6.5 when unretrospected merges reach `--retro-threshold` (and always once at drain). Tripwires fire from step 7, after `tripwires` prints (bullet below). The letters are stable IDs, not loop order — within a wave, the retrospective's D (step 6.5) fires *before* C (step 7), except at drain, where step 7's stop condition runs the final 6.5 pass after it. The Retrospective subagent only proposes; every disposition is the human's:

- **Batch into one grilling.** Refactor proposals via `AskUserQuestion` `multiSelect` (title + summary + evidence PRs per option, ≤4 per question); plan adjustments likewise; open-ended respecs get the inline interview. `obsolete` closures are confirmed individually — never inside a multiSelect batch.
- **Approved** → ghost-written side effects only: `/file-ticket` tickets (inserted per the run's issue-set form), issue comments/body edits recording the decision and reasoning, native + prose dependency edges. No Claude/AI attribution anywhere, as always.
- **Declined** → run ledger only, never re-proposed this run, nothing written to GitHub.
- **Tripwires (step 7).** D also fires when `telemetry.mjs tripwires` reports a `tripped` tripwire or a `reviewOverdue` date, in one grilling of its own in step 7. It is never batched into step 6.5's grilling, which has ended by the time step 7 runs `tripwires`. Each one is answered **confirm offline**, **retune** or **dismiss with a reason** (SKILL.md step 7; a dismissal is logged in `references/decisions.md`). `insufficient-data` and `pending-instrumentation` never grill; they ride the wave summary.
- **At drain**, filing tickets re-opens a drained DAG — so the final fork is explicit: ship the new tickets in this run, or leave them filed for a future one.

## Point E — the rate-limit-window fork, and rate-limit-death recovery (resume in place, never re-run the engine)

A rate-limit death is a distinct failure shape from a model failure: the session didn't get anything wrong, it ran out of window mid-work. Step 4 preflights the five-hour window before every engine invocation (`scripts/rate-limit-preflight.mjs`, threshold 0.8) so this should be rare, but the preflight is a heuristic over the *newest* known utilization, not a guarantee — a wave can still start clean and cross the threshold mid-run, or the preflight's source can be stale/absent (it fails open). When step 5 classifies a `failed`/`blocked` row's `failureReason` as `"rate-limited"` (via `classifyFailureReason` in `scripts/lib/rate-limit.mjs` — the report row's structured field when present, else the transcript signature), treat it as an infra failure and follow this recipe rather than the HITL point B grill:

1. **Diagnose without reading the transcript.** SKILL.md forbids reading a session transcript (`<stateDir>/state/logs/issue-<url-encoded-ref>.log` is megabytes of stream-json), so run `node "$SD/scripts/diagnose-failure.mjs" <owner/repo#N> --run-id <runId>` (or `--state-dir <any dir of the run's family>`: either finds the ref's owning report across the run family, and the digest and transcript are read from that report's dir) instead. It classifies the row from the engine's failure digest, else (no digest, or one stamped by a report other than the owner, which `--owner` names; the output's `source` is then `report`, not `digest`) from the transcript itself, by the signature `isRateLimitDeath` checks: a `rate_limit_event` line whose `rate_limit_info.status` is `"rejected"`, and/or the CLI's synthetic rate-limit assistant turn (`error: "rate_limit"`, text "You've hit your session limit"). The reset time (the rejected event's `rate_limit_info.unifiedWindows.five_hour.resetsAt`, epoch seconds) is what `node "$SD/scripts/rate-limit-preflight.mjs" check` reads out of the newest transcripts, so take it from the preflight's output rather than by opening the log. The preflight reads the newest transcripts under the engine base dir, from any run, so its reading can come from another session, not the dead row's. It prints a `resetsAt` only when that reading's five-hour utilization is at or above the threshold (`reason` `reset-soon`, `reset-far` or `window-already-reset`). With no `resetsAt` in its output (`reason` `below-threshold`, `no-utilization-data` or `above-threshold-no-reset-time`, as after a rejection with no five-hour data, such as a weekly-window rejection), the reset time is unknown: do not wait or resume on it, take the row to the point-E grill in item 3 and say there that the reset time is unknown.
2. **Confirm the worktree survived.** The engine's per-issue worktree (`<stateDir>/worktrees/<ref>/...`) is untouched by the death — the session's own commits, if any, are still there. `git -C <worktree> log --oneline -5` and `git -C <worktree> status` to see how far it got before the window closed. Do **not** delete or reset this worktree.
3. **Wait for the reset — or fork to point E.** If `resetsAt` is soon, wait for it (the same wait-vs-ask fork trigger 8 names, shared with the step-4 preflight: print the time, wait if it's within `--wait-max-minutes`, otherwise **this is the point-E grill** — wait / defer / stop).
4. **Launch a continuation agent into the *existing* worktree/branch** — never re-run the engine for that issue. Re-running would create a second worktree/branch and collide with the one the dead session already pushed to (or left committed locally). Carry forward whatever blocking context the dead session was working through when it died (e.g. a pre-PR hook's review text, an open review comment) so the continuation doesn't repeat work or lose the thread. The continuation agent finishes the same implement→push→PR sequence the Implement subagent block describes, from where the dead session left off. Review its PR as step 4d does, with `{REPORT_ID}` = the death report's id (the report whose row died, even when a later report also lists the ref; step 5's `resource` resume in place takes it the same way; any other re-gate takes the id `diagnose-failure.mjs <owner/repo#N> --owner` prints, as step 4d says), even when a later wave is running by then: the continuation is recorded through that report, so its rounds belong to that report's wave.
5. **Telemetry — the death and the continuation are two records.** The death is real telemetry about the window, independent of whatever the continuation later does, so it is recorded even though the issue is not abandoned; if the continuation succeeds, its merge is a *separate* record for the same issue, and the rate-limited attempt is not counted as a bounce on it.
   - **Engine path: never hand-write either record.** Step 6.3's `ingest-wave` derives both from the report, the row's failure digest and `--outcomes`. Give the row's ref the continuation's outcome, as 6.3's table says: `{"pr":N}` when the continuation opened PR N (merged with `finalState` when that PR's last round blocks), or `{"finalState":"blocked-hitl","hitl":{"pointB":true}}` when it stalled at point B without a PR. For a `failed` row with no PR whose failure digest (else the row itself) says `failureReason: "rate-limited"`, either outcome makes ingest derive, in this order: the death, with `implStatus: "error"`, `failureReason: "rate-limited"`, `finalState: "deferred"`, `pr: null`, `bounces: 0` and `hitl.pointB: false`; then the continuation, built from the outcome with no rate-limit of its own (a PR gives `implStatus: "pushed"`, and `finalState: "merged"` unless the outcome says otherwise; point B without a PR gives `implStatus: "error"` and the outcome's `blocked-hitl`). With neither a `pr` nor `hitl.pointB` in the outcome (no continuation ran yet), ingest records the death alone, still `deferred`. **A continuation that finishes after its report's 6.3 already ran** (point E's grill chose defer or stop, the wait outlasted the wave, or a later session resumed it) is still recorded through that report: add the continuation's outcome to `$STATE/outcomes/<reportId>.json` (the file 6.3 saved, often `{}`), and re-run 6.3's `ingest-wave` on that report with that file. The re-run derives the death again, finds it in the log and skips it, and appends only the continuation (`scripts/telemetry.test.mjs` pins this). Do this when the continuation reaches its outcome, not at step 7: `audit` counts the death alone as covering a PR-less rate-limit row, so it never names a continuation that was not ingested. Never append the death by hand as well: one with a `finalState` other than `deferred` (or the legacy `error`, which ingest reads as `deferred`) is a second death for the row.
   - **A `lease-wait` or `memory-critical` row resumed in place (SKILL.md step 5's `resource` route) takes the same outcome:** `{"pr":N}` for the continuation's PR, or the point-B `blocked-hitl` outcome when it stalled without one. Without it ingest records the stop alone, and `audit` counts that deferred death as covering the row, so it never names the missing continuation. Add it to `$STATE/outcomes/<reportId>.json` and re-run 6.3 when the continuation finishes, as above.
   - **Fallback paths (`workflow`, `inline`): hand-write the death at death time.** The instant step 5 classifies the row as rate-limited, append its record: `implStatus: "error"`, `failureReason: "rate-limited"`, `finalState: "deferred"` (see `scripts/telemetry.mjs`). The continuation's merge is an ordinary step-6 emission.

   Either way, `report()` excludes every `failureReason: "rate-limited"` record from the model-quality indicators (first-pass yield, triage-miss, bounce rate) — an infra death must never make those numbers look worse than the model actually performed — and tallies it instead in the report's `quotaFailures` count (see *Telemetry* in `SKILL.md`).

## Resource stops — rows the engine stopped for memory pressure or a lease wait

A row whose `failureReason` is `memory-critical` or `lease-wait` (`stopStage` `launch`, `retry`, `post-check` or `session`) did not fail on the model's work: the engine stopped it. Step 5's `resource` route sends a PR-less one here, never to point B, and the worktree decides:

- **Commits or a dirty tree** (`git -C <worktree> log` against the base, and `git -C <worktree> status`): resume in place, as for point E. Launch a continuation agent into the existing worktree and branch; never re-run the engine for that issue, whose existing branch it would collide with.
- **A clean worktree with no commits**, whatever the `stopStage`: re-run it on a spec filtered to the stopped refs (`scripts/lib/wave-spec.mjs`), emitted into its own suffixed state dir. The original config is never re-run: the engine's `prepareIssues` skips only `succeeded` rows, so it would relaunch `failed` rows (with or without PRs) into their existing branches, the collision the point-E rule above forbids.

Run the resource preflight first (wait, then ask at point F). After a ref's second resource stop in a run, go to HITL point F whatever the pressure instead of resuming or re-running it again: the preflight returns `proceed` at every pressure below `critical`, so busy lease slots alone could otherwise repeat the stop forever. A continuation agent that gives up on the lease (its return ends with the closing line `orchestrator-stop: lease-wait`, or on the fallback it returns `status: "error"` with `notes: "lease-wait"`) is not an engine row, so the route counts it itself: it counts as that ref's next resource stop. A stopped row that has a PR is gated, with `ciStatus` `"fail"` for a `retry` stop and `"none"` for any other, and the CI profile runs before it is queued (SKILL.md step 5). Telemetry records the stop as `failureReason: "memory-critical"` or `"lease-wait"`, left out of the model-quality indicators as `"rate-limited"` is.

### Engine death

When the engine process itself dies mid-wave it writes no report, and its report is rebuilt by hand from the state files. Whoever rebuilds it stamps each row that was running `status: "failed"`, `failureReason: "engine-died"`, and a row rebuilt without it ingests as a model error. A death the engine recorded itself needs no stamp: its report rows carry `engineDeaths: [{at}]` (claude-orchestrator#315, oldest first, omitted when there are none), and `ingest-wave` records one death record for each (`implStatus: "error"`, `finalState: "deferred"`, `failureReason: "engine-died"`, `ts` the death's `at`) ahead of the row's own record, which becomes the continuation; the engine writes each marker when it next starts, so every marker is an earlier death than the report's own, and a stamped row keeps its own death record beside them. A death is recorded once, whichever report is ingested first: a marker that a later report re-lists keeps its `at`, and a marker is the death of the latest report of the same config to start (`startedAt`) before the marker and after the row's previous marker. When that report stamped the row `engine-died` and the row derives an `engine-died` record of its own (`implStatus: "error"`), the marker records nothing: the death is that report's own record (the hand-stamped record, or the pre-#286 model-error record of that report, which only that report's id proves), with the dead run's sessions, whichever report is ingested first, and `audit` names the row until that report is ingested. A stamped row that kept a PR is gated, not dead, and derives no death of its own, so the marker records the death. Whoever rebuilds a dead engine's report by hand keeps the dead run's own `startedAt`, never the rebuild time: it is what places the report before the marker. A relaunch that died without writing a report is no such report, so a marker that lists its death but not the death before it is taken for the earlier report's; a real model error is never folded into a marker. A marker's death takes no session cost: the row's sessions are its continuation's. `engineDeaths` is the canonical channel; #398's SIGTERM stamp records only the death of the run it stamps. Reports from before claude-orchestrator#315 carry no `engineDeaths` and ingest as before. No session wrote a terminal record, so ship-dag reads the reason from the row and never infers it from a transcript, a pid file or a wall-clock gap. It is infrastructure like a resource stop: step 5 routes it as `resource` (never point B), and `ingest-wave` records it with `implStatus: "error"`, `finalState: "deferred"` and `failureReason: "engine-died"`, left out of the model-quality indicators as `"rate-limited"` is. Recover each row as a resource stop is (resume in place when the worktree has commits or a dirty tree, else a filtered re-run), then record the outcome. A row resumed in place gets its outcome in `$STATE/outcomes/<reportId>.json`, and 6.3's `ingest-wave` is re-run on the rebuilt report, which appends only the outcome. A re-run row's outcome is recorded by the filtered re-run's own ingest; do not also add it to the rebuilt report's outcomes, or the outcome is recorded twice. Until one of them does, `audit` names the ref in `engineDied`. A ref deferred at point F stays named: its deferral and its death are one record.

## Point F — resource pressure (`critical-hitl`)

claude-orchestrator owns the threshold table and the machine-wide lease; ship-dag's column of it is that nothing new starts at `critical`. Waiting does not relieve memory pressure, so the wait cap (15 minutes, re-checked each minute through `--sleep-before 60 --waited-minutes <total waited before this call>`; the script adds the call's own sleep) ends in asking, never in starting. Point F guards four steps, and each answers its three questions differently:

| Guarded step | Triggers point F | "wait" resets | "Start anyway" does |
| --- | --- | --- | --- |
| Engine invocation | the step-4 preflight reads `critical-hitl`: `critical` after 15 minutes waited | the summed-wait counter, to 0 | an inline `CO_PRESSURE_OVERRIDE=critical-as-warning` prefix plus `--parallel 1` on the engine command |
| Step 6.2 CI re-run | summed lease waits pass 15 minutes at `critical`, or pass 30 minutes at any pressure | the summed lease-wait counter, to 0 | at `critical` a rerun with the inline override on that one command; at non-critical pressure a plain rerun, since the override changes nothing below `critical` |
| Review/fix hand-off | the step 4d/5 preflight reads `critical-hitl`, or one PR returns `lease-wait` twice in a run | the summed-wait counter, to 0, and that PR's return count | hands over exactly 1 PR, with no override prefix: none reaches an Agent-tool subagent, so its heavy commands may still read `critical` and end in the `lease-wait` give-up, which the main agent says when it offers the choice |
| Resource-stop route | step 5's preflight reads `critical-hitl` before a resume or re-run, or a ref stops for resources a second time in a run, whatever the pressure | the summed-wait counter, to 0, and that ref's stop count, after waiting 10 minutes (below `critical` the preflight returns `proceed` at once, so without the pause the next attempt meets the same busy slots) | at `critical` a filtered re-run takes the engine row's override; below `critical` a plain resume or re-run, with no override and no `pressureOverride`, since the override changes nothing there; a continuation agent takes the hand-off row's rule |

The four choices:

- **wait**: keep re-checking, and reset what the table's "wait resets" column names for the guarded step (each row names its counters: reset the summed-wait counter to 0 for a fresh cap, plus whatever else the row lists), so the loop asks again only after another full cap; without the reset every re-check would return `critical-hitl` at once.
- **start anyway**: does what the table's "Start anyway does" column says for the guarded step, and nothing more. Where that column names `CO_PRESSURE_OVERRIDE=critical-as-warning`, it is an inline prefix on that one command (never `export`ed), with `--parallel 1` when the command is the engine, i.e. `CO_PRESSURE_OVERRIDE=critical-as-warning … run.mts wave --parallel 1`. Everything that invocation starts (its sessions, the hook that admits their heavy commands, the engine's post-session checks) reads `critical` as `warning`: one session at a time, one heavy slot. Every other process on the machine still reads `critical` and gets 0 slots. The override covers that one invocation; the next wave's preflight asks again. `critical-as-warning` is the only accepted value.
- **defer this step**: leave it for a later run.
- **stop the run**.

**Telemetry.** When the user chooses "start anyway" for an engine invocation, the main agent stamps `pressureOverride: true` in the `--outcomes` of that engine invocation's report for each row (for a filtered re-run, only in the re-run report's file), and `ingest-wave` carries it onto the derived records (`deriveWaveRecords` passes it through; `normalizeRecord` keeps unknown keys). When a row's rate-limit death was resumed at point E, the flag lands on the death record, because the death is the session the overridden engine ran; the continuation is a separate resume that ran without the override, so it does not carry the flag.

## A remote host that cannot run its sub-wave, and remote rows

Step 4b routes a remote script's exit on `EXIT` (`scripts/lib/remote.mjs`). Two outcomes come here; the rest are in SKILL.md's table.

- **The host cannot start its sub-wave** (exit `3`, unreachable with nothing changed or started on it; or exit `1` from `host-sync-claude`/`host-prepare`, a failed sync or CLAUDE.md or lease-hook drift that `host-prepare` still refuses after the sync). Only this host's sub-wave stops; the other hosts' launch. Ask once, with the failing step and its message: **run its issues locally** (re-emit them with the host moved to `local`; nothing was launched there, so nothing can race), **wait** (retry the failed script when the host is back or the drift is fixed, not on a timer), or **defer** (leave its issues `pending`; if the user stops the run, give them `{"finalState":"deferred"}`, step 6.3). A host that answered `255` or `4` from `host-run` is not this case: its engine may still be running, so it is resumed with `--collect-only` and its issues are never run locally.
- **Remote rows** (step 5's `resource` route on a row whose wave sidecar line's `host` is not `local`). The local session can neither inspect nor continue in a worktree under the host's state dir, so the commit count and dirty flag are read over ssh and a row with commits or a dirty tree goes to point E with three choices: **re-run it on the host** (a filtered re-run: a new `--by-host` emit into its own suffixed dir, `host-prepare`, `host-run`), **continue locally from the pushed branch**, or **defer**. Nothing runs a continuation session on the host. If the host worktree no longer exists, say so and offer the same three. A clean worktree with no commits is the filtered re-run on the same host, as for a local row.

## What does NOT escalate

- PLAUSIBLE (unconfirmed) findings, or findings outside `--block-on` categories — surfaced in the summary, not blocking.
- Retro items the subagent judged not worth a ticket — its block demotes them to `observations` (payoff-ranked, ≤5 proposals typical); observations never grill, they ride the wave summary. A PLAUSIBLE proposal that *did* make the cut still grills — confidence is surfaced at point D, not filtered before it.
- A tripwire in state `insufficient-data` or `pending-instrumentation` — named in the wave summary, never grilled.
- Cosmetic nits — listed for the human, never block a merge.
- A CONFIRMED finding in a gated category outside `correctness`/`security` that carries a usable `mergeOrder` note — a merge-order clearance, counted in `mergeOrderClearedCount` and named on the gate's stderr line, so the human sees what the other PR owes. The note is read again at the rebase gate (SKILL.md step 6.2), where any note that mentions the PR or its issue, or sits in the PR's own rounds, escalates to the full review.
- A CONFIRMED finding the reviewer itself marked `blocking: false`, outside `correctness`/`security` — scored as a nit, and named in the gate's `selfClearedCount`/`selfCleared[≤3]` so the human can second-guess the downgrade in the wave summary without it stopping the wave.
- A green PR — auto-merges under the requester-authorized policy (see the skill's Merge queue).
