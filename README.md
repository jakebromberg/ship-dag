# ship-dag

[![tests](https://github.com/jakebromberg/ship-dag/actions/workflows/tests.yml/badge.svg)](https://github.com/jakebromberg/ship-dag/actions/workflows/tests.yml)

A [Claude Code](https://claude.com/claude-code) skill that ships a dependency DAG of already-filed GitHub issues to `main`, **one wave at a time**. Each issue flows through the cheapest capable subagent — Haiku triage, Sonnet implement, Opus review — and lands via rebase-and-merge, **auto-merged on green**. The main agent owns everything human-facing and stateful (DAG discovery, the ready-set, the HITL gates, the dependency-ordered merge queue); the expensive parallel implement→review work fans out to subagents.

The premise: a well-specced issue Sonnet-implements and survives the Opus gate cleanly. When that premise breaks — an ambiguous spec, a blocking finding, a CI/merge failure — that break is the signal to stop and grill the human.

Between the merge queue and the next wave, a **retrospective pass** (one read-only Opus subagent) reviews the merged surface holistically — the cross-PR duplication that per-PR review structurally misses, and remaining-plan drift — and, after human approval (HITL point D), files ghost-written refactor tickets into the remaining DAG and applies plan adjustments.

On an epic run, each wave is filed as its own sub-epic of the epic (label `ship-dag-wave`, titled `<epic title> — wave K`), with the wave's issues moved under it while it runs and any that did not merge moved back when it closes, so the epic's sub-issue tree reads wave by wave.

See [`SKILL.md`](./SKILL.md) for the full skill definition and the wave loop.

## Dependency: claude-orchestrator

The parallel **implement** fan-out is delegated to the [claude-orchestrator](https://github.com/jakebromberg/claude-orchestrator) engine — per-repo worktrees + CI, per-issue model/effort, `mergePolicy: "none"` (implement, run CI, open a PR, then STOP; the Opus review gate and merge queue stay in the skill). Point `CO_HOME` at a checkout of that repo (default `~/Developer/claude-orchestrator`); its `dist/` must be built (`npm run build` — `dist/` is committed, so a fresh clone already has it).

Engine sessions run under claude-orchestrator's machine-wide lease hook (`CO_LEASE_HOOK=on`, set inline on step 4b's engine invocation). The agent rules, pinned by `scripts/lease-rules.test.mjs` in `scripts/engine/prompt.md`, SKILL.md's Implement and Review blocks and `workflow.js`: a heavy command may wait minutes for a slot and must run in the foreground; a `lease: no slot after <n>s` denial means rerun, never a test failure or a reason to skip CI; after the second denial the session stops, comments on the issue, ends with the line `orchestrator-stop: lease-wait` and exits without pushing; never wrap a command in `cli-lease.js`. Lease reruns are not infra-failure retries under the Guardrails. Review and fix hand-offs are sized from lease capacity: steps 4d and 5 read `recommendedHandoff` from `resource-preflight.mjs` (`max(1, capacity − live.length)`, 0 at `critical`) before each hand-off, and a hand-off subagent that gives up on the lease returns its PR to the queue (`scripts/handoff-rules.test.mjs`).

## Project resolution (org-agnostic)

ship-dag resolves the target project from context, never assuming an org:

- **Repo** — a fully-qualified `owner/repo#N` wins; else inferred from the cwd (`gh repo view`); else `--org O` with a bare `repo`.
- **Org checkout root** (where per-repo worktrees are created) — derived from the resolved repo's checkout, i.e. the parent of `git rev-parse --show-toplevel`. Override with `SHIP_DAG_REPOS_DIR` (or `SHIP_DAG_PROJECT_ROOT`, which the skill already emits).
- **Checkout name and worktree location** — a repo's checkout is normally the directory named after it, with worktrees in an adjacent `<checkout>-worktrees/`. When no directory carries the repo's name, the engine uses the one whose `origin` remote is that repo (a submodule path or renamed clone), skipping linked worktrees and plain subdirectories of an enclosing repo. That scan is one level deep, so the org checkout root must be the directory directly holding the checkout (for a submodule, its parent inside the superproject, e.g. `wxyc-ios-64/Shared`). A SwiftPM package whose `Package.swift` declares a `.package(path: "../…")` dependency (line and nested block comments ignored) gets its worktrees beside the checkout instead, named `<checkout>--<slug>`, so those paths keep resolving; an existing path there that is not one of the repo's worktrees is refused. `SHIP_DAG_WORKTREE_MODE=sibling|adjacent` overrides the detection for every repo in the run (an unknown value warns and is ignored). Each repo's layout is resolved once per run. See `scripts/engine/repo-layout.mjs`.
- **Per-repo base branch + local CI** — a repo declares its local CI by committing an executable `scripts/ci` at its root, which ship-dag runs from the worktree root (call it directly, not through `sh`, so the machine-wide lease hook classes it as heavy). An entry in [`references/repo-ci-profiles.json`](./references/repo-ci-profiles.json), keyed by `owner/repo`, overrides it with its own commands and can pin the base branch; without an entry the base branch is the repo's default branch. Whether `scripts/ci` exists, and that it is executable, is read from the base branch on GitHub, never the PR branch, so a branch cannot switch its own check on or off; what runs is the worktree's copy, so a branch that weakens `scripts/ci` is the review gate's to catch. A non-executable `scripts/ci`, or a repo or base branch GitHub cannot find, stops step 4 with the reason. A repo with neither runs with no post-session check (the emitter warns — an unverified wave is the dangerous failure mode).

## ETA of a run

```bash
node scripts/eta/run.mjs [--run <runId>] [--state-base <dir>] [--json]
```

Estimates when a run will land its last ticket. With no `--run` it takes the newest run under `${XDG_STATE_HOME:-~/.local/state}/ship-dag/engine` (by the start its id encodes) that holds a fetched DAG. That DAG is step 1's `fetch --members` output saved in the run's dir as `dag.json` (or `dag.new.json`, a refetch), beside step 2's `plan` output as `plan.json` (or `plan.new.json`); a run that kept its spec only in a temp file has no ETA. It reads the run's state dirs read-only (whichever of `dag.json`/`dag.new.json` is newer, likewise the plan, each ticket's first and latest engine start under `state/metadata/`, and the PR each report row names, across the run's wave and retry dirs) and asks GitHub for every ticket's state and merge time in **one** batched GraphQL query. It prints the ETA as a range in Pacific time with the zone label, the binding constraint, a per-repo table (merged, left, service time, finish), throughput, remaining waves, the blocked tickets it left out, and the as-of time (a run whose open tickets are all blocked has no ETA: it prints `ETA: none, waiting on N blocked tickets` and its binding constraint is `blocked`); `--json` prints the same as data, except that its `binding` is an id where the text shows a display name (`bindingName`'s). The three limit ids (`queue:<owner/repo>`, `pace` and `waves`) are also the ids of the bar's limit markers; `blocked` and `done` name no marker, since either one means there is no ETA to mark.

| `binding` (JSON) | Text output | Meaning |
|---|---|---|
| `queue:<owner/repo>` | `queue <owner/repo>` | that repo's merge queue |
| `pace` | `throughput` | overall merge pace |
| `waves` | `depth` | remaining waves times wave latency |
| `blocked` | `blocked` | only blocked tickets are open; no ETA |
| `done` | `done` | nothing is open |

Progress goes to stderr. Exit 0 printed, 1 no run or no fetched DAG, 64 usage.

The model (`scripts/eta/model.mjs`, pure) takes the latest of three limits:

- **Per-repo merge queue.** A repo merges one PR at a time, and each merge makes the next PR in that repo rebase, re-check and re-run CI. Its service time is the gap between consecutive merges of the run's PRs in that repo, over the last 6 gaps between merges (7 merges); with fewer than 2 merges it falls back to 15 minutes. Finish = now + tickets left in the repo × service time.
- **Throughput.** The gap between consecutive merges anywhere in the run, over the last 12 gaps, × tickets left.
- **DAG depth.** The plan's waves that still hold an open ticket × one ticket's latency: from its latest engine start (the newest `startedAt` in `state/metadata/issue-<ref>.json` across the run's dirs) to the latest review round its gate does not block (that round file's mtime, matched by `reviewRoundFiles` and judged by the review gate under the run's own `blockOn`). The merge-queue wait is left out, since the queue limit already counts it. A ticket with no passing round yet adds no sample. Only the 8 most recent review passes set the latency (`latencyWindow`), so a ticket that sat overnight stops stretching the late end once newer passes arrive, and once more than 8 have passed the output says it is using the latest 8. Of those, samples above the median plus 3 median absolute deviations (`latencyTrimK`) are trimmed as outliers (the deviation is floored at 10% of the median, so a window of equal samples still trims a far one), and the output says how many; if fewer than 3 samples would survive the trim, nothing is trimmed. Below 3 samples depth uses a 2-hour default, and the output says how many samples it had. A session resumed by hand outside the engine writes no metadata, so its latency runs from its last engine start.

Each limit is a range: the 25th, 50th and 75th percentiles of its samples give the optimistic, likely and pessimistic finish, and the binding constraint is the limit with the latest likely finish. Only merges since the run started count (the run id's local time, or the first engine start if that is earlier). A merge time is the merged PR's `mergedAt`: the PR a report row names, else a PR that closed the issue, else the issue's `closedAt`; an issue closed as not planned or as a duplicate has none. When several reports across the run's dirs (wave dirs and retry dirs alike) name a ticket's PR, the one that started last wins. Tickets the plan lists as `blocked` or `cyclic` (an external blocker or a human decision) are listed and not counted while they are still open. Without `gh` the estimate falls back to the fetched DAG's open set with no merge times, and says so; when GitHub resolves only some of the query (an issue transferred or deleted), the rest is used and a note names what it could not resolve.

### On the status line: the `ship-dag-eta` mod

This repo is also a plugin marketplace (`ship-dag`, in [`.claude-plugin/marketplace.json`](./.claude-plugin/marketplace.json)) that lists one Claude Code mod, `ship-dag-eta`, in [`plugins/ship-dag-eta/`](./plugins/ship-dag-eta). Install it from a terminal session:

```text
/plugin install ship-dag-eta --marketplace jakebromberg/ship-dag
```

Answer `y` to add the marketplace, then pick a scope. From a local clone instead: `/plugin marketplace add ~/Developer/ship-dag`, then `/plugin install ship-dag-eta@ship-dag`.

At session start and every two minutes after, the mod finds the newest run under the state base and, when that run's dirs changed in the last six hours, pins one status line: a 20-cell bar, the merged count, then `ETA <likely> (<early> to <late>), bound by <constraint>, as of <time>`, every time in Pacific with its zone label. With no active run the line is cleared. `/ship-dag-eta-bar` opens a pane (never on its own, and without taking focus) that draws the run as a progress bar over time: the axis runs from the run's start to the late ETA, filled up to now and shaded from the early to the late ETA, with a glyph beneath for each point of interest (now `▲`, early `‹`, likely `◆` and late `›` ETA, each repo queue's likely finish by its initial, overall pace `~`, waves left `≡`) and a legend giving each one's Pacific time and which is binding. A marker that shares a cell gives way to the binding one (the legend still lists it), and one past the end clamps there with an arrow. A run whose open tickets are all blocked draws no ETA markers and says `waiting on N blocked tickets` on the status line and in both panes, rather than that nothing is left. Below 60 columns the pane draws the compact bar, the likely ETA and the binding constraint instead. `/ship-dag-eta [runId]` prints the CLI's full block for the active run, or for the run named whatever its age. Each refresh recomputes from the run's local state; GitHub's answer is kept in the plugin's store for five minutes, so the sessions running the mod share one GraphQL query per five minutes. Depth's review passes are the review gate's verdicts, and the gate is Node code in the ship-dag skill, so the mod runs the installed skill's `scripts/eta/review-passes.mjs` through `node` (from `~/.claude/skills/ship-dag`, cached the same way); without the skill, depth uses its default and the estimate says why. The model, the state reader and the bar layout live in `plugins/ship-dag-eta/lib/`, because an installed plugin cannot reach outside its own folder; `scripts/eta/` re-exports them, so the CLI, the mod and the `node --test` suite share one copy.

## Tests

```bash
node --test 'scripts/**/*.test.mjs' 'eval/**/*.test.mjs'
```

The mod's own tests run under the engine's test kit: `claude plugin test plugins/ship-dag-eta`, and `claude plugin validate .` checks the marketplace, the manifest and the hooks module.

The suite loads the topo-sort core, so `CO_HOME` must point at a checkout of [claude-orchestrator](https://github.com/jakebromberg/claude-orchestrator) with its deps installed (`npm ci` there — `dist/` is committed, no build). CI ([`.github/workflows/tests.yml`](./.github/workflows/tests.yml)) does exactly this on every push and PR, across Node 22 and 24.

Every mode refuses a host state dir with a character outside `[A-Za-z0-9._/@+-]`, because the dir goes to rsync unquoted (openrsync and rsync >= 3.2.4 disagree on a quoted remote path). The launch records the detached engine's pid in `<host state dir>/host-run.pid`. It polls once a minute (each poll returns at most 256 KiB of log, and a full chunk is followed at once by the next) until the engine process has exited or its report has been there for one poll (the failure digests follow the report), printing the engine log with a `[<host>] ` prefix and appending it to `<local stateDir>/host-<host>.log` (a `--plan` leaves that file alone), then `rsync -a`s only `reports/`, `failure-digest/`, `status/`, `metadata/` and `logs/issue-*` from the host's `state/` into `<local stateDir>/state/`. It never copies `orchestrator.pid`, `logs/orchestrator.log`, `runs/` or `counters/`, which the local engine of the same wave writes under the same dir, and it rewrites no row: the host is recorded on the `--by-host` wave sidecar line (`host`). Exits 0 when a report was written; 1 when the engine exited with none (naming the host's engine log) or a step failed (an ssh or rsync that could not run or whose output overflowed is named as such, not as a drop); 2 on usage; 3 when ssh exited 255 or a call timed out during `--plan` or the pre-launch report check, before any engine started, which is reported as only a drop; 4 when the engine was still running after `--max-wait` minutes (default 360; the message prints the `--collect-only` command); and 255 when ssh exited 255 or a call timed out after the launch, which says nothing about the engine; the message then prints the `--tail` re-attach command and the `--collect-only` command (with absolute paths and the same `--max-wait`). `--collect-only` starts nothing: it resumes the same wait on the pid in `host-run.pid`, then collects, and without that file it says so rather than claiming the engine exited. `--plan` runs the read-only `wave --plan`. `--preflight` runs `resource-preflight.mjs check --parallel K` on the host under the same lease env the engine runs under (`leaseEnv`, one definition in `scripts/lib/host-run.mjs` for both), prints its decision JSON with no `[<host>] ` prefix and nothing else, exits 3 when ssh dropped, and leaves the host log alone. The pure parts are in `scripts/lib/host-run.mjs`; ssh and rsync go through an injected runner. |
