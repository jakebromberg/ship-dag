# Ship a DAG of issues

Walk a dependency DAG of already-filed GitHub issues to `main`, **one wave at a time**. Each issue flows through the cheapest capable subagent — Haiku triage, Sonnet implement, Opus review — and lands via rebase-and-merge, **auto-merged on green**. The skill (you, the main agent) owns everything human-facing and stateful: DAG discovery, the ready-set, the HITL gates, and the dependency-ordered merge queue. The expensive parallel implement→review work fans out to subagents.

The premise: a well-specced issue Sonnet-implements and survives the Opus gate cleanly. When that premise breaks — an ambiguous spec, a blocking finding, a CI/merge failure — **that break is the signal to stop and grill the human** (see `references/escalation-policy.md`).

## When NOT to use

- **One issue, one PR** — just implement it directly.
- **Issues aren't filed yet** — run `/file-ticket` or `/to-issues` first; this skill ships an existing DAG, it doesn't invent one.
- **Exploratory / design-unsettled work** — the DAG must be real dependencies between specced issues, not a research spike.
- **Anything irreversible outside the merge itself** (data migrations gated on manual cutover, infra changes) — ship those by hand.

## Arguments

Parse `$ARGUMENTS` into an **issue set**, an **org default**, and **flags**.

Issue set — one of:
| Form | Meaning |
|---|---|
| `epic#N` / `org/repo#N` | A tracking/epic issue; the DAG is its native sub-issue tree, at any depth. |
| `--label L` | Every open issue in the repo carrying label `L`. |
| `org/repo#12 repo#15 #20` | An explicit set of issue numbers. |

**Org/repo resolution** (no silent org guess):
1. A fully-qualified `owner/repo#N` always wins.
2. Otherwise infer the repo from the current working directory: `gh repo view --json nameWithOwner -q .nameWithOwner`.
3. Otherwise use `--org O` with the bare `repo`. If none of these resolve, **stop and ask** — do not default to an arbitrary org. ship-dag never assumes a particular org: the org checkout root (the dir holding repo siblings) is derived from the resolved repo's checkout — the parent of `git rev-parse --show-toplevel` — and can be overridden with `SHIP_DAG_REPOS_DIR` (see step 4).

The issue set may span repositories. Every node is keyed on its **composite ref** (`owner/repo#N`, or a bare `N` only in a single-repo run), so the same number in two repos stays two distinct nodes and a cross-repo dependency edge is honored end to end. A wave that crosses a repo boundary triggers the cutover gate in step 7.

Hand refs to `/review-loop` as **fully-qualified `owner/repo#N`**: it infers a default org for a bare `repo#N` and looks for the checkout as a sibling of the current working tree (falling back to `gh repo clone`), so a fully-qualified ref keeps it on the right repo. `/cleanup` is org-agnostic — it operates on the current repo's `git worktree list` and detects the default branch dynamically — so it needs no special qualification, but passing it the same fully-qualified ref is harmless.

Flags:
- `--block-on correctness,security` (default) — finding categories that block auto-merge. See `references/review-schema.md`.
- `--max-review-iter K` (default `2`) — `/review-loop` fix passes before escalating a blocking finding.
- `--workflow-threshold N` (default `5`) — **fallback only** (engine unavailable, step 4): a wave with ≥ N cleared issues routes the fallback implement→review through `workflow.js`; below it, inline `Agent` fan-out. Ignored on the primary engine path.
- `--retro-threshold N` (default `3`) — run the step-6.5 retrospective once ≥ N merged PRs have accumulated since the last pass; below N the wave skips it and carries the count forward. A final pass always runs at drain if any unretrospected merges remain. `--no-retro` disables the step entirely (including the drain pass).
- `--dry-run` — print the full wave partition (`waves` / `blocked` / `cyclic`), the per-issue model/effort assignment, and the retro configuration (threshold / disabled), then stop **before any side effect** — step 6.5 never executes on a dry run.

## The wave loop

`SD=$HOME/.claude/skills/ship-dag`. At run start, initialize the run-scoped retro state: `U` (merged-but-unretrospected PR refs, appended in step 6), the wave counter `W` (1-based, incremented on each pass through step 1), and the proposal ledger (retro-filed refs, declined proposals) — step 6.5 consumes and feeds all three. Repeat until the DAG is drained or everything left is blocked on a HITL decision:

### 1. Discover / refresh the DAG

- Run `/recheck-issues` on the issue set first, so state moved by peers/humans since you last looked is picked up.
- **The graph math is delegated, not reimplemented.** `plan-waves.mjs` imports the shared composite-keyed topological-sort core (`readySet`/`layeredTopoSort`) from claude-orchestrator's built `dist/`, so this planner and the engine's `computeWaves` can't drift. Point `CO_HOME` at that checkout if it isn't the default `/Users/me/Developer/claude-orchestrator`; the core must be built there (`npm run build` — `dist/` is committed, so a fresh clone already has it). If the import fails, the script errors with exactly that instruction.
- Build the spec into a temp file. **Single repo:** `SPEC=$(mktemp); node "$SD/scripts/plan-waves.mjs" fetch --repo owner/repo (--epic N | --label L) > "$SPEC"` (or pipe `fetch … | … plan -`). It emits `{ repo, nodes[], edges[], done[] }` keyed on **composite refs**: each node carries `{ number, repo, ref, bodyLen, refCount, labels }` (the last three feed the triage-effort decision), edges are `{ blocked, blockedBy }` ref pairs, and `done[]` holds refs. Sub-issues come from GraphQL `subIssues` (paginated, each keyed on its **own** `repository.nameWithOwner` — a cross-repo sub-issue stays in its home repo, not the epic's). The `--epic` walk is **recursive**: a sub-issue that is itself an epic is descended into, to any depth, in its own repo. Only the leaves become nodes — an intermediate epic is a grouping, not a unit of work, and shipping it would hand a whole sub-tree to one implement subagent. `subIssuesSummary.total` rides along in the parent's response, so a leaf costs no query of its own; a CLOSED sub-issue takes its whole sub-tree out of scope; a cyclic hierarchy terminates with a warning; and an epic whose own sub-issue query comes back unreadable is kept as a single node rather than silently dropped. **An open epic whose descendants are all closed ships as a node** — it isn't a grouping of pending work, it *is* the pending work. Edges are fetched automatically from **two** sources and merged: GitHub's native issue-dependency graph (each node's `blocked_by` list, via `gh api .../dependencies/blocked_by` — tolerant of a repo where it isn't configured or isn't visible to the token) and body-prose `Blocked by #N` / `Blocks #N` / `Depends on #N`, including both the adjacent-clause form ("Blocked by #12, #13 and #14", multi-issue **and** cross-repo `owner/repo#N` refs handled) and a `## Blocked by` / `## Depends on` heading followed by a bulleted list of refs; a bare `#N` is qualified to the citing issue's repo either way. On an `--epic` fetch, edges naming an epic are then rewritten — **before** the merged set is deduped on the `{blocked, blockedBy}` pair, since the rewrite itself can produce the same pair twice on top of the duplicates the two sources already contribute. The rewrite is needed because an epic never ships and so an edge left pointing at one could never be satisfied (it stays open until its last child closes) — stranding its dependent as permanently blocked: an edge between an issue and one of its **own ancestor epics** is containment ("this is part of that", which the native dependency graph surfaces as a `blocked_by` entry), so it is dropped in both directions; every other epic edge is **expanded onto the leaves** — "X is blocked by epic E" becomes "X is blocked by every leaf of E", and an epic's own blocker is pushed down onto each leaf that ships in its place. Closed/merged dependencies are resolved into `done[]`, each viewed in **its own** repo.
- **Multi-repo issue set** (an explicit `org/repo#12 other/repo#15 …` set, or a cross-repo epic): `fetch` takes one `--repo` per call, so fetch once per distinct repo (by `--epic`/`--label`, or hand-build the `nodes[]` for an explicit set) and **union** the results — concatenate `nodes[]`, `edges[]`, `done[]` into one spec, keeping a single top-level `repo` as the default for any still-bare ref. Unioning is safe precisely because every endpoint is a composite ref: same-numbered issues in different repos stay distinct and cross-repo edges survive. (The epic path already unions cross-repo sub-issues for you.)
- On a resumed session — or on an epic run where a cross-repo retro ticket could be attached only by prose (sub-issues are same-repo-only) — **re-union the run's retro-filed refs** into the spec if the fetch didn't surface them. The telemetry CLI has no read subcommand, so read the log file directly (`$SHIP_DAG_TELEMETRY`, else `$XDG_STATE_HOME/ship-dag/runs.jsonl`, else `~/.local/state/ship-dag/runs.jsonl`): the lines with this `runId` and `kind:"retro"` carry `filed[]` — and `declinedTitles[]`, for rebuilding the ledger.
- A dependency counts as satisfied when its issue is **merged or closed** (fetch already folds those into `done[]`) — but see step 7: a *cross-repo* dependency's merge is not enough to auto-release its downstream.

### 2. Compute the ready-set

- `node "$SD/scripts/plan-waves.mjs" plan "$SPEC"` → `{ waves, blocked, cyclic }` (entries are composite refs — `owner/repo#N`, or a bare `N` in a single-repo DAG).
- `waves[0]` is the current ready-set. If `cyclic` is non-empty or `blocked` lists external blockers while nothing is ready, **stop and report** — the DAG can't advance without human input.
- On `--dry-run`: print `waves`, the `blocked`/`cyclic` report, the model/effort each issue would get (per `references/model-effort-matrix.md`), and the retro configuration (threshold / disabled); then stop.

### 3. Triage gate — HITL point A

Fan out **one `Agent{model:"haiku"}` per ready issue, all in a single message** (read-only; see the Triage block). Each returns `{ clear | needs-decision, complexity, questions[], digest }`.

**a. Verify the premises before grilling anyone.** Triage runs on Haiku against the issue text; it is *supposed* to be uncertain about mechanism, and its `questions[]` routinely rest on claims about the code that are simply false. Both `needs-decision` issues in run sd-20260831-162148 did, and checking them **changed both outcomes** — one question dissolved entirely (the column triage wanted to add had no writer to justify it), and the other was unanswerable as asked but sat next to a decidable fact that re-ordered the DAG.

So: for every issue with a non-empty `questions[]`, fan out **one `Agent{model:"sonnet"}` per issue** (read-only; the Premise-check block below), handed that issue's questions. It reads the code and returns one-line verdicts. Grill the human only on what survives — `verdict: "confirmed"` (the premise holds, so the question is real) and `verdict: "undecidable"` (the code cannot settle it; it is a genuine product or design call). A `refuted` question is answered, not deferred: record the refutation as an issue comment and let the issue proceed.

This step exists to keep file-reading **out of main context**. The verification in that run was worth every token it cost — but it was done by reading handlers, migration headers and tests inline, where they persisted for the rest of the run. The conclusions are a few lines; the files they came from are not. Skip the step only when every issue came back `clear`.

**b. Grill once, on what's left.** Collect every surviving question across the wave and **grill the user once** (batch, not per-issue) — `AskUserQuestion` for crisp forks, inline interview for open design questions (`references/escalation-policy.md`). Quote the verifier's `assertion` alongside each question so the human decides against the code as it is, not as triage guessed it to be. Record each resolution as a GitHub issue comment (ghost-writer, no attribution); update the issue body if scope changed.

**Every issue triage returned `oversize: true` joins the same batch**, even one whose `questions[]` is empty — a split is a scope call, and this gate is the last moment it is cheap. Present `sourceEstimate` and `splitHint`, and offer the fork: **split it now** (file the pieces with `/to-issues` or `/file-ticket` in the issue's own repo, encode the edges both ways as at point D, re-fetch at step 1, and let this wave proceed without the parent), or **accept the size** and let it run as one PR. Default to splitting. Splitting an approved plan costs a few minutes; splitting a finished branch costs the branch.
**c. Proceed.** Only **cleared** issues go on. Carry each issue's `complexity` → implement effort, `sourceEstimate` → the implementer's line budget, and `digest` forward; where a premise check corrected the digest's assumptions, carry the corrected version — the engine's implementer reads `digest`, not this conversation.

**d. Telemetry:** emit one record (see *Telemetry* below) for every issue **deferred at this gate** — `finalState:"blocked-hitl"`, `hitl.pointA:true`, `implStatus`/`ciStatus`/`reviewVerdict` null. These point-A records are what make the triage-miss and HITL-A indicators measurable instead of survivor-only.

### 4. Implement fan-out — the engine implements, the skill reviews

The parallel **implement** work is delegated to the **claude-orchestrator engine** — per-repo worktrees + CI, per-issue model/effort, and its default `mergePolicy: "none"` (implement each issue in its own worktree, run that repo's CI, open a PR, then **STOP** — never merge). The **Opus review gate stays here**, as a ship-dag pass over the PRs the engine opens. `CO_HOME` points at the engine checkout (default `/Users/me/Developer/claude-orchestrator`, the same core import as step 1).

**Preflight (before every engine invocation, including a retry).** A wave launched while the account's five-hour rate-limit window is already near-exhausted is near-certain to die mid-implement, at the most expensive possible moment. Run:
`node "$SD/scripts/rate-limit-preflight.mjs" check` (optionally `--base-dir`/`--threshold`/`--wait-max-minutes` to override the defaults — 0.8 utilization, 30-minute wait cap). It reads the newest `rate_limit_event` out of the newest-by-mtime session transcripts under `${XDG_STATE_HOME:-$HOME/.local/state}/ship-dag/engine/*/state/logs/issue-*.log` (every run's transcripts live under that one base dir — see step 4a), walking a few candidates newest-first — not just the single newest file — so a just-created, still-empty log can't shadow an older transcript that actually has a reading, and prints a JSON decision on stdout:
- `action: "proceed"` (below threshold, or no readable utilization source at all — **fail-open**: a fresh machine with no prior runs must not be blocked by absent telemetry) → continue to 4a.
- `action: "wait"` (at/above threshold, window resets within 30 minutes) → print `resetsAt`, sleep until it, then re-run the preflight and continue.
- `action: "hitl"` (at/above threshold, reset is further off or unknown) → **stop and grill the human — HITL point E**: wait / defer this wave / stop the run (`references/escalation-policy.md`).

**a. Emit the engine config.** Build a ready-wave spec (JSON): for each **cleared** issue `{ number, repo, ref, title, complexity, sourceEstimate?, model?, effort?, digest, extraDirs? }` — carry triage's `complexity` (the engine derives effort from it) and its `sourceEstimate` (emit-config folds the budget into the issue's `description`, since the engine interpolates a fixed variable set and would pass an unknown `{{SOURCE_ESTIMATE}}` through to the prompt verbatim); set `model`/`effort` only where triage or the rubric overrides. Add `repos` from `references/repo-ci-profiles.json` for the wave's distinct repos (each `{ baseBranch, commands }`; a repo absent there defaults to `main` + no CI — emit-config warns); `name: "ship-dag-<runId>"`; an absolute per-run `stateDir` **outside any repo** (e.g. `${XDG_STATE_HOME:-$HOME/.local/state}/ship-dag/engine/<runId>`); `projectRoot` = the org checkout root `$PROJECT_ROOT`, derived once as `PROJECT_ROOT="${SHIP_DAG_REPOS_DIR:-$(dirname "$(git rev-parse --show-toplevel)")}"` — the parent of the target repo's checkout in the sibling layout; set `SHIP_DAG_REPOS_DIR` to override (e.g. a meta-repo root like `/Users/me/Developer/daisyguide`); `promptTemplate` = `$SD/scripts/engine/prompt.md`. Then:
`node "$SD/scripts/emit-config.mjs" spec.json > "$STATE/config.json"`. Every ready-wave issue is independent, so emit-config gives each `dependsOn: []` — one flat wave the engine runs fully in parallel.

**b. Invoke the engine.** Export `CO=${CO_HOME:-/Users/me/Developer/claude-orchestrator}` once. Preview first (read-only, no side effects — the analog of `--dry-run`):
`SHIP_DAG_CONFIG="$STATE/config.json" CO_HOME="$CO" npx --prefix "$CO" tsx "$SD/scripts/engine/run.mts" wave --plan`
then run it:
`SHIP_DAG_CONFIG="$STATE/config.json" SHIP_DAG_PROJECT_ROOT="$PROJECT_ROOT" CO_HOME="$CO" npx --prefix "$CO" tsx "$SD/scripts/engine/run.mts" wave --parallel K`.
`SHIP_DAG_PROJECT_ROOT` also feeds the worktree layer's repos dir (via `reposDirFromEnv`'s fallback in `hooks.mts`), so this single env var keeps both the `--detach` respawn root and the per-repo worktrees under `$PROJECT_ROOT` — no WXYC path is assumed. Export `SHIP_DAG_REPOS_DIR` explicitly only if the two must differ.

**c. Read the report.** The engine writes `<stateDir>/state/reports/<id>.json`. Each row is keyed on the composite **`ref`** (`owner/repo#N`) — the disambiguator for same-numbered cross-repo issues — plus `number`, `status`, `prUrl`, `prNumber`. A `succeeded` row means the engine ran that repo's CI green before opening the PR (`retryOnCheckFailure` retried once, else the row is `failed`), so treat it as `ciStatus: "pass"` and map its `ref`→`prNumber` (branch via `gh pr view <PR> --json headRefName` if the review needs it). The engine writes a routed diagnosis for every non-succeeded row after each wave (`state/failure-digest/issue-<encoded-ref>.json`); step 5 reads it via `scripts/diagnose-failure.mjs`. **`status` alone does not tell you whether work landed** — a session can commit, push, and open a PR and *then* die on a quota stop, leaving a `failed` row with a real, green PR (run sd-20260831-162148: `failed` + `prNumber: 625`, every check green). So route on the **PR**, not the status: a `failed`/`blocked` row **with** a `prNumber` goes to the review gate exactly like a `succeeded` one, and only a `failed`/`blocked` row with **no PR** is an implement stall → **HITL point B** (step 5). Never retry a row that has a PR — the branch already exists, and the engine's own generated report recommends `--retry-failed` without making this distinction.

**d. Review pass (Opus — stays in the skill).** For each opened PR, run the **Review** subagent (the verbatim block below) over the PR's diff against **its own** base branch. Hand it `{REVIEW_PATH}` = `$STATE/reviews/<url-encoded-ref>.json` (`mkdir -p "$STATE/reviews"` first); it writes the full finding schema there and returns `{ issue, path, findingCount, headline }` — a couple of hundred bytes rather than the whole finding set.

Then compute the gate from the file, never from the subagent's word for it:
`node "$SD/scripts/review-gate.mjs" "$STATE/reviews/<url-encoded-ref>.json" --block-on "$BLOCK_ON"` → `{ issue, verdict, blockingCount, nitCount, findingCount, blocking[≤3], unknownCategories[], path }`. It applies `references/review-schema.md`'s rule (`category ∈ --block-on` **and** `verdict == CONFIRMED`) deterministically, and refuses to read a review with no `findings` array as clean — a truncated file must not auto-merge. This yields the same per-issue result the fallback paths do — `{ issue, ref, branch, pr, ciStatus, review:{ verdict, blockingCount, blocking[], path }, openQuestions[] }` — which step 5 reconciles. **Read `path` only when you act on the findings** (routing to `/review-loop`, or quoting them to a human); the gate decision itself never needs them.

**Fallback (engine unavailable — `CO_HOME` unset/unbuilt, or the invocation errors):** revert to the pre-C1 path. Cleared count ≥ `--workflow-threshold` **and** `Workflow` available → `Workflow({ scriptPath: "$SD/workflow.js", args: { repo, blockOn, reviewDir: "$STATE/reviews", issues: [{ number, digest, complexity, implEffort, reviewEffort }] } })`; else inline `Agent` fan-out (one Implement per issue in a single message, Review each as it returns). Both blocks are still present and produce the same result shape. The engine is preferred: it actuates per-issue effort literally, isolates per-repo worktrees + CI, and survives `--detach` — the fallback keeps ship-dag working without the engine checkout.

**Mixed-repo waves:** the engine handles them natively (per-issue `repo` → per-repo worktree, base branch, and CI), where `workflow.js` takes a single `repo` per batch. In practice a single ready wave rarely mixes repos, since cross-repo edges fall on wave boundaries where step 7's point-C gate already stops you.

### 5. Reconcile each result

- **Green** — CI pass, gate `verdict` not `blocking`, no open questions → queue for merge. Carry `nitCount` and `path` into the wave summary; a `nits-only` PR's findings are worth a human's eye, but reading them is *their* call, not a cost the run pays automatically.
- **Blocking finding** (`blockingCount > 0`) → hand `/review-loop` the PR and the review `path` — `/review-loop owner/repo#PR --max-iter K` (from *you*, the main agent — reliable Skill access). Converges to green → queue. Doesn't clear within `--max-review-iter`, or needs a design call → **HITL point B**. On a bounce, the retried implement runs one effort tier higher (rubric guardrail 2).
- **Any `failed`/`blocked` row — diagnose it in ONE call before deciding anything:**
`node "$SD/scripts/diagnose-failure.mjs" <owner/repo#N> --run-id <runId>` (or `--state-dir <stateDir>`). It returns `{ status, prNumber, prUrl, exitCode, failureReason, route, terminal }` in a few hundred bytes — the row, the rate-limit classification, the engine's exit code, and the session's terminal `result` record. The engine already wrote that object for every non-succeeded row as the wave finished (`<stateDir>/state/failure-digest/issue-<encoded-ref>.json`, streamed while the transcript was hot); this reads it, and recomputes the same shape from the report and transcript for a run that was never digested. **Never `cat`/`tail`/`grep` `<stateDir>/state/logs/issue-*.log` yourself**: despite the name those are full stream-json session transcripts, not logs in the skim-me sense — routinely megabytes (1.1MB in sd-20260831-162148) — and pulling one into context costs more than the wave it describes. Act on `route`:
  - `review-gate` — a PR is open, whatever the status says. The implement work landed; gate it like a `succeeded` row (step 4d) and let step 6 merge it. **Do not retry**: the branch exists and the work may already be merged.
  - `point-E` — no PR, died on quota. **Infra failure, not a model failure**: ≤2 manual retries, resume-in-place per the point-E recovery recipe in `references/escalation-policy.md` (never re-run the engine for that issue — it would collide with the existing branch; a wait that runs long forks to the point-E grill, not point B).
  - `point-B` — no PR, ordinary implement stall → **HITL point B**. `terminal.reason` is the session's own last word on why; quote it in the grill rather than re-deriving it.
- **Open question surfaced mid-implementation / non-flaky CI failure / judgment-needing merge conflict** → **HITL point B** (grill), then re-queue or defer the issue.
- **Telemetry:** emit one record for every issue that **terminates here** without merging (`blocked-hitl` / `deferred` / `error`), capturing `implStatus`, `ciStatus`, `reviewVerdict`, `failureReason`, `findings[]`, `bounces`, and `hitl.pointB`. A `"rate-limited"` `failureReason` record is emitted here **at death time** regardless of what happens next — even though the issue isn't actually abandoned, it's resumed in place per the recovery recipe (`references/escalation-policy.md`'s point E) and, if the continuation succeeds, gets a *second*, ordinary `merged` record at step 6 for the same issue. `report()` (`scripts/telemetry.mjs`) excludes `"rate-limited"` records from the model-quality indicators so this interim record never dilutes them — see *Telemetry* below.

### 6. Merge queue — auto on green

Side-effecting; all on you, the main agent; serialized in **dependency order**. Per queued PR:

1. `git fetch`; rebase the PR branch onto the latest tip of **its own repo's base branch** — not a hardcoded `main`. Resolve it per repo (`gh repo view owner/repo --json defaultBranchRef -q .defaultBranchRef.name`, or `git rev-parse --abbrev-ref origin/HEAD`); e.g. `wxyc-ios-64` is `master`.
2. **If the rebase moved the base** (a sibling from this wave already merged under it — the normal dependent-wave case): **re-run BOTH local CI and the Opus review gate** and re-check `--block-on` before merging. A verdict computed pre-rebase does not carry over once the base changed. If the re-gate now finds a blocking issue, pull the PR back into step 5.
3. `gh pr merge --rebase`.
4. `/cleanup owner/repo#PR` — remove the worktree, delete the branch, fast-forward, prune.
5. **Telemetry:** emit one record (`finalState:"merged"`, plus the **worst** `reviewVerdict` seen for the issue — a bounced-then-merged issue logs `blocking`, not the post-fix `clean`, so triage-miss and review-catch stay measurable rather than survivor-biased — `bounces`, and `path`) for the merged issue — see *Telemetry* below.
6. Append the merged issue's ref and PR number to `U`, the run's unretrospected-merge list — the input to step 6.5.

**Never loop-retry a failing CI or merge.** ≤2 manual retries on an infra failure, then stop and surface the failure + cost. No `while`-loops against a red run.

### 6.5 Retrospective — HITL point D

Per-PR review is structurally blind to cross-PR problems: parallel implementers in separate worktrees cannot see each other's work, and the plan's remaining specs were written before this wave's code existed. This pass looks at the run holistically — after the merge queue, before advancing.

**Trigger:** skip unless `|U| ≥ --retro-threshold` (default 3 merged PRs; print the carry-forward count when skipping). **Always run once at drain** — when step 7's stop condition is met with `|U| > 0` — regardless of threshold. `--no-retro` disables both. A pass consumes `U` (reset to empty) whatever it finds, and emits one `kind:"retro"` telemetry record.

**Fan out ONE `Agent{model:"opus"}`** (read-only; the Retrospective block below — this block has exactly one copy, here) with: the merged issue refs + PR numbers in `U`, rendered as `owner/repo#N (PR #M)` pairs so `gh pr diff` has the PR number (all repos); the remaining DAG (`nodes[]` refs+titles and `edges[]` from the current spec, **minus every issue merged this run** — the spec predates this wave's merges, so without the subtraction the plan pass would audit just-shipped issues as pending); the run's issue-set form (epic / label / explicit set); and the run ledger (previously filed retro-ticket refs, previously declined proposals). Hand it `{RETRO_PATH}` = `$STATE/retro/wave-<W>.json` (`mkdir -p "$STATE/retro"` first). It writes the full `references/retrospective-schema.md` envelope there — `{ mergedPrs, refactors[], planAdjustments[], observations[] }` — and returns that same envelope **minus every `body` and `proposal`**, the two long fields, plus a stable `id` per proposal. That is exactly what point D's checkboxes need; the drafted text is only needed for proposals the human actually approves, and most are declined. The main agent stamps `wave: W` when emitting the telemetry record; the subagent never produces it.

**HITL point D** (protocol in `references/escalation-policy.md`): if `refactors` and `planAdjustments` are both empty, print `observations` in the wave summary and move on — no grilling. Otherwise **batch everything into one grilling**, mirroring point A:

1. Present refactors via `AskUserQuestion` with `multiSelect` — one option per proposal (title + one-line summary + evidence PR refs), recommended-first; ≤4 options per question, paginate if more. Plan adjustments likewise; an open-ended `respec` gets the inline grill-me-style interview instead of a checkbox.
2. **Approved refactors** → fetch each approved proposal's drafted text one at a time, by id: `node "$SD/scripts/retro-pick.mjs" "$STATE/retro/wave-<W>.json" R1`. Never read the whole retro file back — the declined proposals' bodies are the bulk of it and nothing needs them. Then ghost-write one ticket each via `/file-ticket`, **in the refactor's `repo`** — never the cwd default, which on a multi-repo run may contain none of the code (the drafted `body`; the `complexity` tier as triage context) — then insert into the run's DAG by issue-set form: **epic run** — attach as a native sub-issue of the epic (sub-issues are same-repo only; a cross-repo refactor ticket instead gets a prose `## Related` link to the epic AND is appended to the in-context set explicitly); **`--label L` run** — apply label `L` to the new issue; **explicit-set run** — append the fully-qualified `owner/repo#N` to the in-context issue set. Encode each approved `blockedBy`/`blocks` edge **both ways** so step 1's two merged edge sources pick it up: the native dependency graph AND body prose (`Blocked by owner/repo#N`). A refactor whose implementation consumes another repo's just-merged artifact must also carry a `Blocked by` edge naming that **merged** upstream issue — fetch folds it straight into `done[]`, so it never blocks, but the cross-repo edge is what routes the ticket through step 7's point-C cutover gate instead of letting it auto-release against an unpublished artifact.
3. **Approved plan adjustments** → ghost-written issue comments recording the decision and reasoning; body edits where the spec changed (`respec`); native edge add/remove plus matching body-prose edit (`add-edge`/`drop-edge`); `gh issue close --reason "not planned"` with an explanatory comment (`obsolete` — the one destructive act: confirm it individually in the grilling, never inside a multiSelect batch); `split` files children via `/file-ticket` and respecs the parent.
4. **Declined proposals** → recorded in the run ledger only; nothing written to GitHub; never re-proposed this run.
5. Filed tickets flow into the next step-1 fetch and ship through the normal triage→implement→review pipeline — the retro itself never writes code and never merges.
6. **If the just-filed tickets are the only thing keeping the run alive** — this pass ran in drain mode, *or* it ran at threshold on what would otherwise be the run's final wave (ignoring the tickets it just filed, step 7's stop condition would hold) — ask one final crisp fork: ship them **in this run** (loop back to step 1) or **leave them filed** for a future `/ship-dag` invocation (run ends). Filing tickets must never silently extend a run that was about to end; this question is the loop's termination valve.

**Telemetry:** emit one `kind:"retro"` record per pass — `{ kind:"retro", runId, wave: W, mergedPrs, proposedRefactors, approvedRefactors, declinedRefactors, proposedAdjustments, approvedAdjustments, declinedAdjustments, filed[], adjusted[], declinedTitles[] }` (see *Telemetry* below; `declinedTitles` persists the declined half of the ledger — titles only — so a resumed run can rebuild it, with point D backstopping near-duplicate re-proposals the title match misses).

### 7. Advance — HITL point C on any cross-repo cutover

Mark merged issues done; go to step 1. The re-fetched `done[]` will surface the next wave.

**Cross-repo cutover gate — "satisfied" ≠ "merged" across a repo boundary.** A merged upstream PR is not consumable downstream until it is published/deployed (e.g. `wxyc-shared` → GH Packages → `Backend-Service`; a BS deploy → the canary validates it live). So when a newly-ready issue becomes ready **because a dependency in a *different* repo just merged**, do **not** auto-release it — **stop and grill the human** to confirm the upstream artifact is actually consumable (package published, service deployed, migration cut over), or that a named gate command succeeded, before triaging/implementing that dependent. Same-repo edges keep releasing automatically; only an edge crossing a repo boundary (or into a manual deploy/publish step) gates here. This mirrors the "anything irreversible outside the merge itself → ship it by hand" rule. A deferral here emits a `blocked-hitl` telemetry record, as at point B.

Stop when `waves` is empty (drained) or the only remaining issues are blocked on a HITL decision you've already surfaced. **When the stop condition holds and `|U| > 0`, execute the step-6.5 block once more (drain mode) before the wave summary** — its substep-6 fork governs whether the loop returns to step 1 (ship the just-filed tickets now) or the run ends (leave them filed).

At the end, print a **wave summary**: per issue — final state (`merged` / `blocked-hitl` / `deferred` / `error`), PR number, review verdict, and any nits or routed findings for the human; and per retrospective pass — proposals made/approved/declined, tickets filed (refs), plan adjustments applied, and any `observations`.

## Subagent instruction blocks

Include the relevant block **verbatim** in each subagent's prompt (the inline fallback path). The **Premise-check** block (step 3a) and the **Retrospective** block have exactly one copy each — both always run from the main agent on every path. The **Implement** block has two other copies — `scripts/engine/prompt.md` (the engine's template, the primary path) and `workflow.js` (the accelerator fallback); the **Review** block is mirrored in `workflow.js`. Keep all copies in sync when editing. The Review block runs from the skill on every path (the engine implements only), so it is the one block that is never skipped. The **Retrospective** block has exactly **one** copy (below): it always runs from the main agent after the merge queue on every path — engine, workflow, and inline — so there is no mirror to keep in sync.

### Triage (Haiku, read-only)

> **Task:** Read GitHub issue `{OWNER/REPO}#{N}` and its linked context. Decide whether an implementer could proceed without guessing at intent. Do **not** write code or touch the repo.
>
> 1. `gh issue view {N} --repo {OWNER/REPO} --json title,body,labels`. Follow referenced issues (`#\d+`) enough to understand dependencies and scope.
> 2. Judge **clarity**: is the desired end state, the "where" (files/paths/symbols), and the acceptance criteria unambiguous? Flag any true open question (ambiguous spec, an architectural fork, a new third-party dependency) — not mere implementation latitude.
> 3. Judge **complexity**: `mechanical` (config/string/dep bump, single file, no logic) · `normal` · `complex` (multi-file, algorithmic, concurrency, schema/migration, public API, or security surface).
> 4. Judge **size**: `sourceEstimate`, the added lines of *production source* this issue needs — excluding tests, generated data, and docs, which carry most of a diff's volume but little of its review risk. Estimate from the issue's scope against the code it names, not from how long the issue text is. Over **200** means it is too big to land as one reviewable PR: set `oversize: true` and use `splitHint` to name the seam it would cut on — the abstraction that should land first, the layer that could ship alone, the mechanical extraction separable from the behaviour change.
>
> **Return:** `{ status: "clear" | "needs-decision", complexity: "mechanical|normal|complex", sourceEstimate: <integer>, oversize: <boolean>, splitHint: "..." | null, questions: [ ... ], digest: "2-3 sentence implementation plan" }`.

### Premise-check (Sonnet, read-only)

> **Task:** Triage flagged `{OWNER/REPO}#{N}` as needing a decision. Each of its questions rests on a claim about how this code actually works, and triage read only the issue text — it did not read the code. Your only job is to check those claims. Do **not** write code, answer the design question, or touch the repo.
>
> Questions from triage: `{QUESTIONS}`
>
> 1. For each question, name the factual premise it assumes (e.g. "this table has writers other than X", "this status grants an entitlement", "this function has multiple callers").
> 2. Settle that premise **against the code**: find the callers, the writers, the readers, the migration that created the column, the test that pins the behaviour. Cite `file:line`.
> 3. Verdict per question: `refuted` — the premise is false, so the question dissolves (say what is true instead); `confirmed` — the premise holds, so the question is a real decision; `undecidable` — the code cannot settle it, because it is a product or design call.
> 4. An `undecidable` question often sits next to a fact that *is* decidable and that changes the answer — a table with zero readers, rows that predate the accounts they reference, a caller that passes one constant forever. State it. It is frequently more useful than the question asked.
> 5. Be brief and be specific. One or two sentences per `assertion`, each one something a reader could check from the `evidence` alone. Do not summarize the issue, restate the question, or explain your search.
>
> **Return:** `{ issue, premises: [{ question, verdict: "refuted|confirmed|undecidable", assertion, evidence: ["path/to/file.ts:42"] }] }`. No Claude/AI mention anywhere.

### Implement (Sonnet, own worktree)

> **Task:** Implement `{OWNER/REPO}#{N}` in a fresh, disposable git worktree. Digest from triage: `{DIGEST}`.
>
> 1. Locate the repo checkout (sibling under `/Users/me/Developer/`, else `gh repo clone`). `cd` in. Read repo + package `CLAUDE.md` and the patterns in the module you're touching; match them.
> 2. Test-first: failing test → smallest correct implementation → passing test. No drive-by refactors — every extra change is something the review will flag.
> 3. Run the repo's local CI (lint/format/typecheck/tests, or `npm run ci:*`). Fix red before pushing; never push known-red to bait the review.
> 4. **Size check — run it as you work, and again before you commit.** Your budget is the one stated in the digest above, or **200 added lines of production source** if it names none. Tests, generated data, and docs sit *outside* the budget and must never be trimmed to fit it. Measure with `git diff --stat "$(git merge-base HEAD "origin/$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name)")"` and count only the source files. Within budget, or over by less than half → carry on. **Over by more than half → stop and cut**: take the change back to the last point where the tests pass and the slice stands on its own, push *that*, and record the remainder — what you left undone and the seam you cut on — under a `## Deferred` heading in the PR body and in `splitRemainder`. A narrow PR that lands beats a complete one that stalls in review; the retrospective files the remainder as its own ticket.
> 5. Commit (**ghost-writer: no Claude/AI attribution anywhere**), push a dedicated branch, open a PR whose body contains `Closes #{N}` and cross-references the issue.
> 6. **If you hit a genuine open question mid-implementation** that the issue + repo conventions don't answer, STOP: return `status: "blocked"` with the questions — do **not** push a guess.
>
> **Return:** `{ issue, status: "pushed|blocked|error", branch, pr, ciStatus: "pass|fail|none", openQuestions: [ ... ], splitRemainder: "..." | null, notes }`.

### Review (Opus, own worktree)

> **Task:** You are the last code-review gate before `{OWNER/REPO}#{N}` (PR `#{PR}`, branch `{BRANCH}`) reaches its base branch. Nothing downstream catches your misses — reason exhaustively.
>
> 1. In your worktree: `cd` into the checkout, `git fetch`, `gh pr checkout {PR}` (or check out `{BRANCH}`).
> 2. Review the PR against **its own base branch** (`git diff origin/$(gh pr view {PR} --json baseRefName -q .baseRefName)...HEAD`, or simply `gh pr diff {PR}`) — do not assume `main`; this repo's base may be `master`. Cover correctness, security, simplification, efficiency, and test coverage.
> 3. Optionally, if the Skill tool is reachable, also run the built-in `/code-review` and union its findings. If not reachable, your inline review stands alone.
> 4. Classify **each finding** per `references/review-schema.md` — `category` and `verdict: CONFIRMED | PLAUSIBLE`. Do **not** decide the overall gate yourself: `scripts/review-gate.mjs` recomputes it from your findings, so a merge never turns on a model's claim about its own output.
> 5. **Write the full schema object to `{REVIEW_PATH}`** — `{ issue, findings: [{ category, verdict, file, line, summary, failure_scenario }] }` — and return only the summary below. Your findings are read from that file at the moment they're actually needed (a `/review-loop` route, or a report to the human); returning them inline instead would park every one of them in the orchestrator's context for the rest of the run.
>
> **Return:** `{ issue, path: "{REVIEW_PATH}", findingCount, headline }` — `headline` being one line naming the most serious finding, or `"no findings"`. No Claude/AI mention anywhere.

### Retrospective (Opus, read-only)

> **Task:** You are the retrospective pass for this run — per-PR review sees one PR at a time; you see the run as a whole. Nothing downstream re-examines the merged surface — reason exhaustively across it. Since the last retrospective these PRs merged: `{MERGED_PRS}` (pairs of composite issue ref and PR number, `owner/repo#N (PR #M)`, possibly spanning repos — the PR number is what `gh pr diff` takes). The remaining DAG is `{REMAINING_NODES}` (refs + titles) with edges `{REMAINING_EDGES}`. Already filed by earlier retrospectives: `{FILED_REFS}`. Previously declined by the human — do **not** re-propose these or trivial variants: `{DECLINED}`. Do not write code, comment on issues, or modify anything — you propose; the human disposes.
>
> 1. Read each merged PR's diff against its own base: `gh pr diff {PR} --repo {OWNER/REPO}` and `gh pr view {PR} --repo {OWNER/REPO} --json title,body,files`. For the plan pass, read each remaining node's spec: `gh issue view {N} --repo {OWNER/REPO} --json title,body,labels`. Work from diffs; open files at the merged tip (sibling checkout under the org root) only where a diff alone is ambiguous. No worktrees, no checkouts of your own.
> 2. **Cross-PR pass:** over the union of the diffs, find what per-PR review structurally misses — near-duplicate logic landed by parallel implementers, the same problem solved two ways (pattern divergence), extract-helper/shared-module opportunities, duplicated test fixtures or setup. A cross-PR finding must cite **≥2 merged PRs** as evidence, at least one not itself a retro-filed ticket's PR (no refactors of refactors); a single-PR finding belongs to the review gate that already ran — drop it.
> 3. **Plan pass:** reread each remaining node's spec against what actually merged. Flag: a stale spec (merged code changed the ground it assumed — `respec`), a wrong or missing dependency (`add-edge` / `drop-edge`), an issue whose work already landed incidentally (`obsolete`), an issue the merged reality has made too big (`split`). A merged PR body carrying a `## Deferred` heading is an implementer telling you it cut itself short against its line budget: the remainder named there is a `split` proposal with the evidence already written — draft it as a ticket rather than re-deriving it from the diff. Propose the smallest edit that makes the plan true again, with the evidence PR(s).
> 4. For each refactor: classify with the review vocabulary (`category` from the finding schema; confidence `CONFIRMED | PLAUSIBLE`), assign a `complexity` tier (`mechanical|normal|complex` — it sets implement effort if the ticket ships), name the `repo` the ticket belongs in (the run may span repos; the ticket's home is where its code lives, not where the run started), suggest `blockedBy`/`blocks` edges against remaining nodes where ordering matters — plus an edge naming a **merged** upstream in a *different* repo whose artifact the refactor consumes (it never blocks, but it routes the ticket through the cross-repo cutover gate) — and draft a ticket `body` to the `/file-ticket` bar: problem, desired end state, where (files/symbols from the evidence), acceptance criteria, evidence PRs as context links.
> 5. Rank refactors by expected payoff and keep the list short (≤5 typical) — a laundry list buries the two that matter. Anything real but not worth a ticket goes in `observations`. Nothing you return gates a merge; everything you saw already shipped.
>
> 6. Give every proposal a stable `id` — `R1, R2, …` for refactors, `P1, P2, …` for plan adjustments, in the ranked order of step 5. **Write the full envelope to `{RETRO_PATH}`**, then return that envelope with each proposal's `body` (refactors) and `proposal` (plan adjustments) **omitted**. Those two fields are long, and only the proposals the human approves ever need them — they are fetched back by id from the file. Everything else stays in the return: point D's grilling renders from titles, summaries, evidence and edges.
>
> **Return** the retrospective schema (`references/retrospective-schema.md`) minus the drafted text: `{ path, mergedPrs, refactors[{ id, title, repo, category, confidence, summary, locations, evidence, complexity, suggestedEdges }], planAdjustments[{ id, ref, kind, rationale, evidence, edge }], observations[] }`. No Claude/AI mention anywhere.

## Telemetry

Every issue that reaches a terminal-for-this-wave state emits one JSON record — and every retrospective pass emits one run-scoped record — to an append-only run log, so leading indicators — Sonnet first-pass yield, triage-miss rate, review bounce/catch, HITL frequency, retro proposal/approval volume — are tracked across runs nearly for free. Emission is wired at the five points they actually occur (**step 3** point-A defer, **step 5** blocked/deferred/error, **step 6** merged, **step 6.5** one retro record per pass, **step 7** point-C deferral), not batched at the end.

- **Append** (best-effort — a telemetry failure must never abort a wave): `node "$SD/scripts/telemetry.mjs" append '<json>'` (or `@file` / `-` for stdin). The record is validated and `ts`-stamped on write. Schema: `{ runId, repo, issue, complexity, triageStatus, assignment, path, implStatus, ciStatus, reviewVerdict, failureReason, findings[], reviewPath, bounces, hitl:{pointA,pointB}, finalState, pr, tokens }`; `findings[]` carries the gate's `blocking[]` summary (≤3 one-liners) rather than the full set, and `reviewPath` points at the review file holding all of them — the complete findings are never lost, they just stop being re-ingested to be logged; `implStatus`/`ciStatus`/`reviewVerdict` are `null` for issues that stop at triage. Mint one `runId` per `/ship-dag` invocation. Records carry a `kind` discriminator — `"issue"` (the default; stamped when absent, so pre-existing logs stay valid) or `"retro"` (the step-6.5 pass record — a different shape, validated separately and excluded from every per-issue indicator; see `scripts/telemetry.mjs`).
- **`failureReason`** is `null` except alongside `implStatus: "error"` for a rate-limit death, where it's `"rate-limited"` (see step 5 and `references/escalation-policy.md`'s point-E recovery recipe) — a distinguishable marker `report()` uses to separate quota failures from model failures: `"rate-limited"` records are excluded from the model-quality indicators (first-pass yield, triage-miss, bounce rate) and tallied instead in the report's `quotaFailures` count (`renderReport()` prints a `quota failures:` line whenever it's non-zero), so a quota outage never makes those numbers look worse than the model actually performed.
- **`path`** records `"engine"` (primary — implement via the orchestrator, review from the skill), `"workflow"`, or `"inline"` (the two fallbacks). Effort is actuated literally on `engine` (implement sessions) and `workflow`; the `engine` path's review gate and the whole inline `Agent` fan-out are *nominal* (prompt-approximated — the `Agent` tool has no `effort` param), so the report never treats inline effort as actuated.
- **`tokens`** is `null` on the inline path (per-agent token counts aren't exposed to the orchestrator); real cost attribution lives in the eval harness, not here.
- **Report:** `node "$SD/scripts/telemetry.mjs" report [--since ISO]` prints the indicators (JSON to stdout, table to stderr), broken down by complexity tier.
- **Storage:** append-only JSONL *outside* the repo — `$SHIP_DAG_TELEMETRY`, else `$XDG_STATE_HOME/ship-dag/runs.jsonl`, else `~/.local/state/ship-dag/runs.jsonl` — so collected run data can never be accidentally committed.
- **Tests:** `node --test "skills/ship-dag/scripts/**/*.test.mjs"`.

## Guardrails (non-negotiable)

- **Anonymity** — no Claude/Claude Code attribution in commits, PRs, issue comments, anywhere. Ghost-writer mode.
- **Worktree per issue** — created before any code; removed via `/cleanup` after merge.
- **CI before push** — local lint/format/typecheck/tests must pass before any push.
- **No auto-retry loops** — ≤2 manual retries on infra failure, then stop and report cost.
- **Data safety** — never reset/overwrite collected data; surgical changes only.
- **Never read a session transcript, and never measure with `/context`** — `<stateDir>/state/logs/issue-*.log` are full stream-json transcripts (megabytes); ask `scripts/diagnose-failure.mjs` instead. `/context` itself costs ~15k tokens a call, mostly the deferred-MCP inventory it lists but does not load, so two casual checks can outweigh a wave's actual overhead. To watch a run's context growth for free, sample `wc -c` on this session's transcript (`~/.claude/projects/<project>/<session-uuid>.jsonl`) at the interesting boundaries — launch, engine-done, pre-review, post-merge — and diff the byte counts.
- **Cross-repo cutover is a HITL gate** — never auto-release a wave whose readiness depends on a *different* repo's merge; confirm the upstream is published/deployed/consumable (or a gate command passed) first. "Satisfied" ≠ "merged" across a repo boundary (step 7, point C).
- **The retrospective proposes; it never disposes** — no ticket filed, edge written, spec edited, or issue closed without point-D approval, and it never touches merged code (step 6.5).
- **Auto-merge is a deliberate, requester-authorized deviation** from the house "never auto-merge" rule (`cross-repo-migration`). It is kept tightly behind the green gate (CI pass + no CONFIRMED blocking finding + no open questions), serialized in dependency order, and re-gated after any base-moving rebase. `--dry-run` and the five HITL points (A triage, B implement/review, C cross-repo cutover, D retrospective, E rate-limit window) are the escape hatches.
