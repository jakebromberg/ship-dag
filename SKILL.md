# Ship a DAG of issues

Walk a dependency DAG of already-filed GitHub issues to `main`, **one wave at a time**. Each issue flows through the cheapest capable subagent — Haiku triage, Sonnet implement, Opus review — and lands via rebase-and-merge, **auto-merged on green**. The skill (you, the main agent) owns everything human-facing and stateful: DAG discovery, the ready-set, the HITL gates, and the dependency-ordered merge queue. The expensive parallel implement→review work fans out to subagents.

The premise: a well-specced issue Sonnet-implements and survives the Opus gate cleanly. When that premise breaks — an ambiguous spec, a blocking finding, a CI/merge failure — **that break is the signal to stop and grill the human** (see `references/escalation-policy.md`).

## When NOT to use

- **One issue, one PR** — just implement it directly.
- **Issues aren't filed yet** — run `/file-ticket` or `/to-issues` first; this skill ships an existing DAG, it doesn't invent one.
- **Exploratory / design-unsettled work** — the DAG must be real dependencies between specced issues, not a research spike.
- **Anything irreversible outside the merge itself** (data migrations gated on manual cutover, infra changes) — ship those by hand.

## Arguments

Parse `$ARGUMENTS` into an **issue set**, an **org default**, and **flags**.

Issue set — one of:
| Form | Meaning |
|---|---|
| `epic#N` / `org/repo#N` | A tracking/epic issue; the DAG is its native sub-issue tree, at any depth. Each wave of an epic run is filed as its own sub-epic of it (steps 3c and 7). |
| `--label L` | Every open issue in the repo carrying label `L`. |
| `org/repo#12 repo#15 #20` | An explicit set of issue numbers. |

**Org/repo resolution** (no silent org guess):
1. A fully-qualified `owner/repo#N` always wins.
2. Otherwise infer the repo from the current working directory: `gh repo view --json nameWithOwner -q .nameWithOwner`.
3. Otherwise use `--org O` with the bare `repo`. If none of these resolve, **stop and ask** — do not default to an arbitrary org. ship-dag never assumes a particular org: the org checkout root (the dir holding repo siblings) is derived from the resolved repo's checkout — the parent of `git rev-parse --show-toplevel` — and can be overridden with `SHIP_DAG_REPOS_DIR` (see step 4).

The issue set may span repositories. Every node is keyed on its **composite ref** (`owner/repo#N`, or a bare `N` only in a single-repo run), so the same number in two repos stays two distinct nodes and a cross-repo dependency edge is honored end to end. A wave that crosses a repo boundary triggers the cutover gate in step 7.

Hand refs to `/review-loop` as **fully-qualified `owner/repo#N`**: it infers a default org for a bare `repo#N` and looks for the checkout as a sibling of the current working tree (falling back to `gh repo clone`), so a fully-qualified ref keeps it on the right repo. `/cleanup` is org-agnostic — it operates on the current repo's `git worktree list` and detects the default branch dynamically — so it needs no special qualification, but passing it the same fully-qualified ref is harmless.

Flags:
- `--block-on correctness,security,convention,contract` (default) — finding categories that block auto-merge. See `references/review-schema.md`.
- `--max-review-iter K` (default `2`) — `/review-loop` fix passes before escalating a blocking finding.
- `--workflow-threshold N` (default `5`) — **fallback only** (engine unavailable, step 4): a wave with ≥ N cleared issues routes the fallback implement→review through `workflow.js`; below it, inline `Agent` fan-out. Ignored on the primary engine path.
- `--retro-threshold N` (default `3`) — run the step-6.5 retrospective once ≥ N merged PRs have accumulated since the last pass; below N the wave skips it and carries the count forward. A final pass always runs at drain if any unretrospected merges remain. `--no-retro` disables the step entirely (including the drain pass).
- `--run-id ID` — resume the run with this id instead of minting a new one (step 1). The id is the `runId` in the run's telemetry records and the name of its dir under `${XDG_STATE_HOME:-$HOME/.local/state}/ship-dag/engine/`.
- `--dry-run` — print the full wave partition (`waves` / `blocked` / `cyclic`), the per-issue model/effort assignment, and the retro configuration (threshold / disabled), then stop **before any side effect** — step 6.5 never executes on a dry run.

## The wave loop

`SD=$HOME/.claude/skills/ship-dag`. At run start, initialize the run-scoped retro state: `U` (merged-but-unretrospected PR refs, appended in step 6), the wave counter `W` (1-based, incremented on each pass through step 1; a resumed session continues it, step 1), and the proposal ledger (retro-filed refs, declined proposals) — step 6.5 consumes and feeds all three. **Mint the run id once, at run start of a new run** (a resumed session recovers the original id instead; see step 1): `node "$SD/scripts/telemetry.mjs" run-id [--label L]` prints `$SHIP_DAG_RUN_ID` when the calling shell has it set, else a fresh `sd-<YYYYMMDD>-<HHMMSS>[-label]` in local time. Use that id for every record, config `name` and dir below. The Bash tool keeps no shell state between calls, so an `export` is gone after the call that made it, and a second `run-id` call mints a different id. So call `run-id` once, and from then on write the literal id it printed into each command: `$RUN_ID` and `$STATE` below stand for that literal and the literal dir path, so either write them out or set them at the start of each Bash call that uses them (`RUN_ID=sd-20261008-153059; STATE=…/engine/$RUN_ID; …`, with the `;`: a prefix assignment such as `RUN_ID=… cmd "$RUN_ID"` does not reach the command's own arguments). Name the id in every wave summary, so it survives compaction. If it is lost anyway, recover it as a resumed session does; never call `run-id` again. **`$STATE` is the run's dir, `<engine base>/<RUN_ID>`** (`${XDG_STATE_HOME:-$HOME/.local/state}/ship-dag/engine/<RUN_ID>`). A wave that gets its own engine `stateDir` is named `<RUN_ID>-<suffix>`, and the suffix must be one that `sameRun` folds: `-w<N>`, `-w<N><letter>`, `-r<N>`, `-resume`, or a single retry letter such as `-b`. Never use a longer label such as `-board`: `audit` and `ingest-wave` find a run's dirs by `sameRun` on the dir name (`runFamilyDirs`), so a dir with any other suffix is invisible to both. Review rounds always go under `$STATE/reviews/`, never under a wave's own suffixed dir (ingest reads the `reviews/` of every family dir only because older runs left rounds in their `-w2` and `-w3` dirs). Repeat until the DAG is drained or everything left is blocked on a HITL decision:

### 1. Discover / refresh the DAG

- Run `/recheck-issues` on the issue set first, so state moved by peers/humans since you last looked is picked up.
- **The graph math is delegated, not reimplemented.** `plan-waves.mjs` imports the shared composite-keyed topological-sort core (`readySet`/`layeredTopoSort`) from claude-orchestrator's built `dist/`, so this planner and the engine's `computeWaves` can't drift. Point `CO_HOME` at that checkout if it isn't the default `/Users/me/Developer/claude-orchestrator`; the core must be built there (`npm run build` — `dist/` is committed, so a fresh clone already has it). If the import fails, the script errors with exactly that instruction.
- Build the spec into a temp file. **Single repo:** `SPEC=$(mktemp); node "$SD/scripts/plan-waves.mjs" fetch --repo owner/repo (--epic N | --label L) > "$SPEC"` (or pipe `fetch … | … plan -`). It emits `{ repo, nodes[], edges[], done[] }` keyed on **composite refs**, plus `members[]` with `--members` (every leaf in scope, closed ones included: the status board's count of the whole issue set, which planning ignores; a wave sub-epic is never a member, but its children are, open or closed; only `--members` makes a `--label` fetch list the label's closed issues too). Each node carries `{ number, repo, ref, bodyLen, refCount, labels }` (the last three feed the triage-effort decision), edges are `{ blocked, blockedBy }` ref pairs, and `done[]` holds refs. Sub-issues come from GraphQL `subIssues` (paginated, each keyed on its **own** `repository.nameWithOwner` — a cross-repo sub-issue stays in its home repo, not the epic's). The `--epic` walk is **recursive**: a sub-issue that is itself an epic is descended into, to any depth, in its own repo. Only the leaves become nodes — an intermediate epic is a grouping, not a unit of work, and shipping it would hand a whole sub-tree to one implement subagent. `subIssuesSummary.total` rides along in the parent's response, so a leaf costs no query of its own; a CLOSED sub-issue takes its whole sub-tree out of scope; a cyclic hierarchy terminates with a warning; and a nested epic that GitHub reports as not found (deleted, or out of the token's reach) is kept as a single node with a warning rather than silently dropped. Any other `gh` failure while listing sub-issues (a rate limit, a 502, expired auth, a malformed page, or sub-issues the token cannot read, which are named) makes `fetch` exit 1 instead: re-run it, or fix the access it names. **An open epic whose descendants are all closed ships as a node** — it isn't a grouping of pending work, it *is* the pending work. The exception is a **wave sub-epic** (label `ship-dag-wave`), which only ever groups one wave's issues: it never ships, even empty or fully merged, and a *closed* one is still descended into, so an issue left open under it is never hidden. Each of those cases warns on stderr. Edges are fetched automatically from **two** sources and merged: GitHub's native issue-dependency graph (each node's `blocked_by` list, via `gh api .../dependencies/blocked_by` — tolerant of a repo where it isn't configured or isn't visible to the token) and body-prose `Blocked by #N` / `Blocks #N` / `Depends on #N`, including both the adjacent-clause form ("Blocked by #12, #13 and #14", multi-issue **and** cross-repo `owner/repo#N` refs handled) and a `## Blocked by` / `## Depends on` heading followed by a bulleted list of refs; a bare `#N` is qualified to the citing issue's repo either way. On an `--epic` fetch, edges naming an epic are then rewritten — **before** the merged set is deduped on the `{blocked, blockedBy}` pair, since the rewrite itself can produce the same pair twice on top of the duplicates the two sources already contribute. The rewrite is needed because an epic never ships and so an edge left pointing at one could never be satisfied (it stays open until its last child closes) — stranding its dependent as permanently blocked: an edge between an issue and one of its **own ancestor epics** is containment ("this is part of that", which the native dependency graph surfaces as a `blocked_by` entry), so it is dropped in both directions; every other epic edge is **expanded onto the leaves** — "X is blocked by epic E" becomes "X is blocked by every leaf of E", and an epic's own blocker is pushed down onto each leaf that ships in its place. Closed/merged dependencies are resolved into `done[]`, each viewed in **its own** repo.
- **Multi-repo issue set** (an explicit `org/repo#12 other/repo#15 …` set, or a cross-repo epic): `fetch` takes one `--repo` per call, so fetch once per distinct repo (by `--epic`/`--label`, or hand-build the `nodes[]` for an explicit set) and **union** the results — concatenate `nodes[]`, `edges[]`, `done[]` into one spec (and, for `--members` fetches, union `members[]` deduped case-insensitively by `refKey`), keeping a single top-level `repo` as the default for any still-bare ref. Unioning is safe precisely because every endpoint is a composite ref: same-numbered issues in different repos stay distinct and cross-repo edges survive. (The epic path already unions cross-repo sub-issues for you.)
- **A resumed session reuses the original run id; it never mints one.** A session is resumed when it is started with `--run-id <id>`, or when the human says it continues an earlier run. **`--run-id` is the explicit override:** take that id, and skip the lookup below. Without it, find the id from two sources (write `$refs` as the set's `owner/repo#N` refs, never bare numbers), each ordered by a clock it defines, never by a record's `ts` (an ingested record's `ts` is its report's finish time, not when it was written):
  - **The telemetry log** (the file the retro re-union bullet below names; `$LOG` stands for its path): the `runId` of the **last line** in file order whose `repo` and `issue` are a ref of this issue set. Lines are appended, so file order is write order. `jq -R -r --argjson refs '["owner/repo#12", …]' 'fromjson? | select(type == "object" and .repo != null and .issue != null) | select((.repo + "#" + (.issue|tostring) | ascii_downcase) as $r | any($refs[]; ascii_downcase == $r)) | .runId' "$LOG" | tail -1`.
  - **The engine dirs' wave sidecars**, which emit-config writes at step 4a, before the engine starts, so they name a run whose first engine wave died before any record existed: every `<engine base>/*/ship-dag-wave.jsonl` entry whose `issues[].ref` holds a ref of this set, with its `runId` and `emittedAt`, newest `emittedAt` last. `jq -R -r --argjson refs '["owner/repo#12", …]' 'fromjson? | select(type == "object" and any(.issues[]?.ref; ascii_downcase as $r | any($refs[]; ascii_downcase == $r))) | [.emittedAt // "-", .runId, input_filename] | @tsv' "${XDG_STATE_HOME:-$HOME/.local/state}/ship-dag/engine"/*/ship-dag-wave.jsonl | sort | tail -3`. An entry without `emittedAt` sorts first; when it is the only candidate, its file's mtime dates it.

  Compare ids as `sameRun` does (a `-w3c` suffix or a `ship-dag-` prefix names the same run). **Use the id only when every source that names one names the same run**, and its dir `<engine base>/<id>` exists (the id without a wave suffix) (`ls -d "${XDG_STATE_HOME:-$HOME/.local/state}/ship-dag/engine/<id>"`; that dir is `$STATE`). **Ask the human, and never guess, when** the log's id and the sidecars' newest id are different runs (the usual case is a run that died in its first engine wave, whose newest log record is an earlier run's over the same issues), when two different runs tie for the newest sidecar entry, when neither source names an id, or when the dir does not exist and the run has had an engine wave. Show the human each candidate id with its source and its clock (the log line, or the sidecar's `emittedAt`). Name the id you use, and where it came from, in the first summary of the session. A wrong id puts the new waves in a second run family, which `audit` and `ingest-wave` never read together with the first.
- **A resumed session continues `W` and the round numbers from what `$STATE` holds; it never overwrites either.** Set `W` one past the highest wave the run has used: the largest `W` among `$STATE/retro/wave-<W>.json` and the numeric part of the `wave` field of every `ship-dag-wave.jsonl` entry in the run's family dirs (`14b` counts as 14). A ref's next review round is one past the highest `N` among its `$STATE/reviews/<stem>.r<N>.json` files (round 1 is `<stem>.json`, so with no `.r<N>` file the next is `r2`). Overwriting `retro/wave-<W>.json` loses that pass's drafted proposals, and overwriting a round file changes its content and resets its mtime, which orders a ref's rounds when any of them has a name other than `<stem>.json` or `<stem>.r<N>.json`. Before writing any of these files, check that the path does not exist.
- **On a resumed session, run `audit` first** (details in step 7): `node "$SD/scripts/telemetry.mjs" audit "$RUN_ID"`. A wave lost to machine sleep mid-queue is found there, and its 6.3 is re-run before the new wave starts. On a resume, **exit 1 is never "no engine wave, move on"**: when stderr says `audit: no dir under … belongs to run …`, the id is wrong (go back to the id-recovery bullet above, or ask the human), and any other exit 1 is the failure its message names. The one exception is a run whose every log record has `path` `workflow` or `inline`: it had no engine wave, so it has no engine dir.
- On a resumed session — or on an epic run where a cross-repo retro ticket could be attached only by prose (GitHub refused the native cross-repo attach) — **re-union the run's retro-filed refs** into the spec if the fetch didn't surface them. The telemetry CLI has no read subcommand, so read the log file directly (`$SHIP_DAG_TELEMETRY`, else `$XDG_STATE_HOME/ship-dag/runs.jsonl`, else `~/.local/state/ship-dag/runs.jsonl`): the lines with this `runId` and `kind:"retro"` carry `filed[]` — and `declinedTitles[]`, for rebuilding the ledger.
- A dependency counts as satisfied when its issue is **merged or closed** (fetch already folds those into `done[]`) — but see step 7: a *cross-repo* dependency's merge is not enough to auto-release its downstream.

### 2. Compute the ready-set

- `node "$SD/scripts/plan-waves.mjs" plan "$SPEC"` → `{ waves, blocked, cyclic }` (entries are composite refs — `owner/repo#N`, or a bare `N` in a single-repo DAG).
- `waves[0]` is the current ready-set. If `cyclic` is non-empty or `blocked` lists external blockers while nothing is ready, **stop and report** — the DAG can't advance without human input.
- On `--dry-run`: on an epic run, print what `wave-epic.mjs sweep --repo <epic repo> --epic N --dry-run` would settle (it writes nothing, and assumes every return would succeed); print `waves`, the `blocked`/`cyclic` report, the model/effort each issue would get (per `references/model-effort-matrix.md`), and the retro configuration (threshold / disabled); then stop.

### 3. Triage gate — HITL point A

Fan out **one `Agent{model:"haiku"}` per ready issue, all in a single message** (read-only; see the Triage block). Each returns `{ clear | needs-decision, complexity, questions[], digest }`.

**a. Verify the premises before grilling anyone.** Triage runs on Haiku against the issue text; it is *supposed* to be uncertain about mechanism, and its `questions[]` routinely rest on claims about the code that are simply false. Both `needs-decision` issues in run sd-20260831-162148 did, and checking them **changed both outcomes** — one question dissolved entirely (the column triage wanted to add had no writer to justify it), and the other was unanswerable as asked but sat next to a decidable fact that re-ordered the DAG.

So: for every issue with a non-empty `questions[]`, fan out **one `Agent{model:"sonnet"}` per issue** (read-only; the Premise-check block below), handed that issue's questions. It reads the code and returns one-line verdicts. Grill the human only on what survives — `verdict: "confirmed"` (the premise holds, so the question is real) and `verdict: "undecidable"` (the code cannot settle it; it is a genuine product or design call). A `refuted` question is answered, not deferred: record the refutation as an issue comment and let the issue proceed.

This step exists to keep file-reading **out of main context**. The verification in that run was worth every token it cost — but it was done by reading handlers, migration headers and tests inline, where they persisted for the rest of the run. The conclusions are a few lines; the files they came from are not. Skip the step only when every issue came back `clear`.

**b. Grill once, on what's left.** Collect every surviving question across the wave and **grill the user once** (batch, not per-issue) — `AskUserQuestion` for crisp forks, inline interview for open design questions (`references/escalation-policy.md`). Quote the verifier's `assertion` alongside each question so the human decides against the code as it is, not as triage guessed it to be. Record each resolution as a GitHub issue comment (ghost-writer, no attribution); update the issue body if scope changed.

**Every issue triage returned `oversize: true` joins the same batch**, even one whose `questions[]` is empty — a split is a scope call, and this gate is the last moment it is cheap. Present `sourceEstimate` and `splitHint`, and offer the fork: **split it now** (file the pieces with `/to-issues` or `/file-ticket` in the issue's own repo, encode the edges both ways as at point D, re-fetch at step 1, and let this wave proceed without the parent), or **accept the size** and let it run as one PR. Default to splitting. Splitting an approved plan costs a few minutes; splitting a finished branch costs the branch.
**c. Proceed.** Only **cleared** issues go on. Carry each issue's `complexity` → implement effort, `sourceEstimate` → the implementer's line budget, `reach` and `decisions` (recorded in the wave sidecar), and `digest` forward; where a premise check corrected the digest's assumptions, carry the corrected version — the engine's implementer reads `digest`, not this conversation.

**Epic runs only, and not on `--dry-run`: open the wave's sub-epic.** `node "$SD/scripts/wave-epic.mjs" open --repo <epic repo> --epic N --refs <cleared refs, comma-separated>` files `<epic title> — wave K` (label `ship-dag-wave`, K one past the epic's highest wave, so a later run continues the sequence), attaches it to the epic, and moves each cleared issue that is the epic's own same-repo child under it — or that is still under an older, still-open wave sub-epic, so two waves never share one; an issue under an intermediate epic or in another repo keeps its parent and is listed in the body. It prints `{ number, wave, moved[], listed[], reused }`; keep `number` for step 7. It is idempotent: a re-run reuses a wave sub-epic a crash left empty, or created but never attached, rather than filing a second. Exit 2 is a refusal before any write; exit 1 means a GitHub call failed partway — run it again. Issues deferred at point A never enter the wave.

Then, still on an epic run, **sweep the older wave sub-epics**: `node "$SD/scripts/wave-epic.mjs" sweep --repo <epic repo> --epic N --except <number>`. Every other `ship-dag-wave` sub-epic of the epic that is still open, or closed with an open issue under it — a lost session's, or a step-7 return that got stuck — has its open issues returned to the epic, gets a comment, and is closed. It runs after `open` on purpose: `open` has already taken this wave's issues out of any stale wave and reused one a crash left empty, so the sweep never undoes a resume. A tidy epic costs one listing per wave and no writes. It prints `{ closed[], returned[], stuck[], errors[] }`; one failing wave is reported in `errors` while the rest still settle, and exit 1 means `stuck` or `errors` is non-empty — report them in the wave summary. On a `--label` or explicit-set run, skip this.

**d. Telemetry:** emit one record (see *Telemetry* below) for every issue **deferred at this gate** — `finalState:"blocked-hitl"`, `hitl.pointA:true`, `implStatus`/`ciStatus`/`reviewVerdict` null. These point-A records are what make the triage-miss and HITL-A indicators measurable instead of survivor-only. Point A's append stays hand-written (no engine report exists for a deferred issue); add `tuningVersion` to it (`node "$SD/scripts/lib/tuning.mjs" resolve version`), as ingest does for engine waves, and write `pr` (where there is one) as a positive integer.

### 4. Implement fan-out — the engine implements, the skill reviews

The parallel **implement** work is delegated to the **claude-orchestrator engine** — per-repo worktrees + CI, per-issue model/effort, and its default `mergePolicy: "none"` (implement each issue in its own worktree, run that repo's CI, open a PR, then **STOP** — never merge). The **Opus review gate stays here**, as a ship-dag pass over the PRs the engine opens. `CO_HOME` points at the engine checkout (default `/Users/me/Developer/claude-orchestrator`, the same core import as step 1).

**Preflight (before every engine invocation, including a retry).** A wave launched while the account's five-hour rate-limit window is already near-exhausted is near-certain to die mid-implement, at the most expensive possible moment. Run:
`node "$SD/scripts/rate-limit-preflight.mjs" check` (optionally `--base-dir`/`--threshold`/`--wait-max-minutes` to override the defaults — 0.8 utilization, 30-minute wait cap). It reads the newest `rate_limit_event` out of the newest-by-mtime session transcripts under `${XDG_STATE_HOME:-$HOME/.local/state}/ship-dag/engine/*/state/logs/issue-*.log` (every run's transcripts live under that one base dir — see step 4a), walking a few candidates newest-first — not just the single newest file — so a just-created, still-empty log can't shadow an older transcript that actually has a reading, and prints a JSON decision on stdout:
- `action: "proceed"` (below threshold, or no readable utilization source at all — **fail-open**: a fresh machine with no prior runs must not be blocked by absent telemetry) → continue to 4a.
- `action: "wait"` (at/above threshold, window resets within 30 minutes) → print `resetsAt`, sleep until it, then re-run the preflight and continue.
- `action: "hitl"` (at/above threshold, reset is further off or unknown) → **stop and grill the human — HITL point E**: wait / defer this wave / stop the run (`references/escalation-policy.md`).

**Resource preflight (beside the rate-limit preflight, before every engine invocation including a retry).** Run `node "$SD/scripts/resource-preflight.mjs" check --parallel <K>`. It reads memory pressure and lease status from claude-orchestrator (`$CO_HOME/dist`) and prints `{ action, reason, level, capacity, live, recommendedParallel, recommendedHandoff }`; it fails open (`proceed`, `reason: "lease-unavailable"`) when `CO_HOME`'s dist lacks the lease API. Nothing new starts at `critical`, and no timer turns a wait into a start:
- `action: "proceed"` (`normal`, `warning-engine-adapts` or `no-signal`) → invoke the engine with `--parallel <recommendedParallel>`; at `warning` the engine adapts live.
- `action: "wait"` (`critical-wait`) → re-run `node "$SD/scripts/resource-preflight.mjs" check --parallel <K> --sleep-before 60 --waited-minutes <total minutes waited before this call>` (0 on the first re-run). The script adds the call's own `--sleep-before` to that total before deciding, and sleeps before it samples, so the loop never needs a foreground `sleep`.
- `action: "hitl"` (`critical-hitl`, after 15 minutes waited) → **stop and grill the human — HITL point F**: wait / start anyway / defer this step / stop the run (`references/escalation-policy.md`). When the user picks "wait", reset the summed-wait counter to 0 (a fresh cap) and resume the `wait` loop; otherwise every re-check would return `hitl` at once. Step 6.2's CI re-run, steps 4d/5's review/fix hand-offs and step 5's `resource` route use the same gate; what triggers point F, what "wait" resets and what "start anyway" does differ per step, and live in the per-step table in `references/escalation-policy.md`. When the user chooses "start anyway" for an engine invocation, stamp `pressureOverride: true` in the `--outcomes` of that engine invocation's report; step 6.3's records carry it (on the death record, not the continuation, when point E resumed a rate-limit death in that report). A filtered re-run of stopped rows (step 5's `resource` route) is its own invocation with its own report: stamp the flag only in that re-run report's outcomes file, never in the original report's.

**a. Emit the engine config.** Build a ready-wave spec (JSON): for each **cleared** issue `{ number, repo, ref, title, complexity, reach?, decisions?, sourceEstimate?, model?, effort?, digest, extraDirs? }` — carry triage's `complexity` (emit-config stamps the implement `effort` from `references/tuning.json`; an issue's own `effort` wins; an issue with no `complexity` takes the config-level `defaultEffort`, also from `tuning.json`; `reach` (`in-diff|repo|external`) and `decisions` (strings) from triage go to the sidecar, not the engine config; an unknown `complexity` or `reach`, or `decisions` that is not an array of strings, makes emit-config exit 2 naming the issue, so fix the triage output and re-emit) and its `sourceEstimate` (emit-config folds the budget into the issue's `description`, since the engine interpolates a fixed variable set and would pass an unknown `{{SOURCE_ESTIMATE}}` through to the prompt verbatim); set `model`/`effort` only where triage or the rubric overrides. Then:
`node "$SD/scripts/emit-config.mjs" spec.json > "$STATE/config.json"`. A wave that needs its own engine `stateDir` (a retry, a resume) gets one named by the suffix rule above and its config goes in that dir. Every ready-wave issue is independent, so emit-config gives each `dependsOn: []` — one flat wave the engine runs fully in parallel.

Export `SHIP_DAG_REPOS_DIR` explicitly only if the two must differ.

**c. Read the report.** The engine writes `<stateDir>/state/reports/<id>.json`. Each row is keyed on the composite **`ref`** (`owner/repo#N`) — the disambiguator for same-numbered cross-repo issues — plus `number`, `status`, `prUrl`, `prNumber`. A `succeeded` row means the engine ran that repo's post-session check green before opening the PR, *if the repo has one* (`retryOnCheckFailure` retried once, else the row is `failed`): treat it as `ciStatus: "pass"`, or as `"none"` for a repo with no `postSessionCheck` in its config entry or at the config's top level, since the engine runs no check there (`emit-config` warns), and map its `ref`→`prNumber` (branch via `gh pr view <PR> --json headRefName` if the review needs it). The engine writes a routed diagnosis for every non-succeeded row after each wave (`state/failure-digest/issue-<encoded-ref>.json`); step 5 reads it via `scripts/diagnose-failure.mjs`. **`status` alone does not tell you whether work landed** — a session can commit, push, and open a PR and *then* die on a quota stop, leaving a `failed` row with a real, green PR (run sd-20260831-162148: `failed` + `prNumber: 625`, every check green). A `succeeded` row **without** a `prNumber` routes to `find-pr` (step 5), not the gate. So route on the **PR**, not the status: a `failed`/`blocked` row **with** a `prNumber` goes to the review gate exactly like a `succeeded` one, and only a `failed`/`blocked` row with **no PR** is an implement stall → **HITL point B** (step 5), unless the engine stopped it for resources (`memory-critical` or `lease-wait`), which step 5's `resource` route takes instead. Never retry a row that has a PR — the branch already exists, and the engine's own generated report recommends `--retry-failed` without making this distinction.

**Rows the engine stopped for resources.** A row's `failureReason` can also be `memory-critical` or `lease-wait`, with a `stopStage` (claude-orchestrator#87): `memory-critical` at `launch` (the issue was never started; the row stays **`pending`**), at `retry` (a retry was refused at `critical`; the row is `failed` after a failed check) or at `post-check` (the post-session check was not run; `failed`), and `lease-wait` at `session` (the agent gave up after its second `lease: no slot` denial and declared `orchestrator-stop: lease-wait`; `failed`, and possibly with commits or a dirty tree). These are infrastructure stops, not model failures, and the engine reports them, so no transcript is scanned for them. A stopped row with a PR still goes to the gate, but its `ciStatus` is not `"pass"`: `"fail"` for a `retry` stop (its check ran and failed), `"none"` for any other stop (no check ran), which is what `diagnose-failure.mjs` returns as `ciStatus` for the row. Step 5 routes them.

**d. Review pass (Opus — stays in the skill).** **Hand-off limit (before each hand-off).** Run `node "$SD/scripts/resource-preflight.mjs" check` and hand over at most `recommendedHandoff` PRs in that invocation (one Review subagent per PR); hand over the rest in later invocations, re-reading the preflight each time. `recommendedHandoff` is `max(1, capacity − live.length)`, 1 when `capacity` is null or the reason is `no-signal`, and 0 at `critical`. Nothing is handed over at `critical`: `critical-wait` waits (re-run with `--sleep-before 60 --waited-minutes <total minutes waited before this call>`) and `critical-hitl` goes to HITL point F. "Start anyway" for a hand-off hands over exactly 1 PR: no environment prefix reaches an Agent-tool subagent, so `CO_PRESSURE_OVERRIDE` cannot apply, and with the lease hook on that subagent's heavy commands still read `critical` and may end in the two-denial `lease-wait` give-up, so say so when you offer the choice. A Review or fix subagent has given up on the lease when its return ends with the closing line `orchestrator-stop: lease-wait` (a `/review-loop` run reports a fix pass that gave up the same way; on the workflow.js fallback, where returns are schema-constrained, a review return with `status: "error"`, `notes: "lease-wait"`, an empty `path` and `findingCount` 0). Check for it before running `review-gate.mjs` or reading a `/review-loop` result as non-convergence, and never run `review-gate.mjs` on such a return. A give-up is not a review verdict and not a model failure, so no round file exists for it (the Review subagent writes none and deletes a partial one it started, so nothing stale sits at `{REVIEW_PATH}` or under `$STATE/reviews/`), put its PR back in the hand-off queue for the next capacity read, and after two such returns for the same PR in a run go to HITL point F. For each opened PR, run the **Review** subagent (the verbatim block below) over the PR's diff against **its own** base branch. Hand it `{REVIEW_PATH}` = `$STATE/reviews/<stem>.json` (`mkdir -p "$STATE/reviews"` first), where `<stem>` = `artifactStem(ref)` (`scripts/lib/failure.mjs`: the ref with `%`, `/` and `#` percent-encoded, so `owner/repo#12` is `owner%2Frepo%2312`). That is round 1; every later round of the same ref (a re-review after a `/review-loop` fix, a re-gate after a rebase moved the base) is `<stem>.r<N>.json` for N = 2, 3, …, never an invented suffix. The subagent writes the full finding schema there and returns `{ issue, path, findingCount, headline }` — a couple of hundred bytes rather than the whole finding set. Also hand it `{TRIGGER}`, which it writes as the file's `meta.trigger`: `"initial"` for round 1, `"review-loop"` for a round that re-reviews a fix after a blocking round (step 5), and `"rebase"` for a re-gate after a rebase moved the base (step 6). Also hand it `{REPORT_ID}`, the stem of the report whose row's PR the round reviews (the `<id>` of `<stateDir>/state/reports/<id>.json` you read at 4c; a PR carried over by a later `--retry-failed` report keeps the original report's id), which it writes as `meta.reportId`: ingest assigns a stamped round to that report's wave whatever its mtime. Every later round of the ref takes the same id. When you no longer hold it from 4c (a step 5 or 6 re-gate after a resume), take it from `node "$SD/scripts/diagnose-failure.mjs" <owner/repo#N> --owner --state-dir <dir>`, which prints the id of the report that owns the ref's latest event without reading a transcript; for a point-E continuation, or step 5's `resource` resume in place, it is instead the death report, the report whose row died and whose outcomes file records the continuation, even when a later report also lists the ref (`references/escalation-policy.md`). Copy the id exactly, without `.json`: a stamp that names no report of the run, or a report that does not list the ref, is warned about and windowed by mtime, as an unstamped round is. Ingest uses `trigger` only as a check: it warns when a later round's trigger is `"review-loop"` but the round before it did not block, or the other way round.

Then compute the gate from the file, never from the subagent's word for it:
`node "$SD/scripts/review-gate.mjs" "$STATE/reviews/<stem>.json" --block-on "$BLOCK_ON" --expect-findings "$FINDING_COUNT"` → `{ issue, verdict, blockingCount, nitCount, selfClearedCount, findingCount, blocking[≤3], selfCleared[≤3], unknownCategories[], malformedBlocking[], path }`. It applies `references/review-schema.md`'s rule (`category ∈ --block-on` **and** `verdict == CONFIRMED` **and** `blocking` is not explicitly `false`) deterministically, refuses to read a review with no `findings` array as clean — a truncated file must not auto-merge — and **fails the same way for a finding whose `category` isn't one of the schema's categories, or is blank/absent**: that finding is folded into `blockingCount` (never `nitCount`) and its category named in `unknownCategories[]`, regardless of `--block-on` or the reviewer's own claimed `verdict`. The `blocking` conjunct only ever narrows, and only within the list `--block-on` names: a CONFIRMED `correctness` or `security` finding that `--block-on` covers blocks on `verdict` alone whatever it says (narrowing `--block-on` past them is still the operator's call, as it always was), a finding omitting it blocks, and a finding carrying a non-boolean (`"false"`, `0`, `null`) blocks with that value named in `malformedBlocking[]` — the field is validated, never coerced. The one direction it can merge something is reported too: a CONFIRMED finding the reviewer cleared with `blocking: false` lands in `selfClearedCount`/`selfCleared[≤3]` as well as `nitCount`, so a downgrade is never bit-identical to an ordinary nit. This yields the same per-issue result the fallback paths do — `{ issue, ref, branch, pr, ciStatus, review:{ verdict, blockingCount, nitCount, selfClearedCount, blocking[], path }, openQuestions[] }` — which step 5 reconciles. Carry `nitCount` and `selfClearedCount` through: step 5 relays both to the human, and a reconciled result that drops `selfClearedCount` auto-merges a reviewer-downgraded CONFIRMED finding with no trace reaching anyone, which is the whole thing the field exists to prevent. **Read `path` only when you act on the findings** (routing to `/review-loop`, or quoting them to a human); the gate decision itself never needs them.

**`--expect-findings` is the subagent's own `findingCount`, and it is not optional in this step.** The gate can recompute a verdict from findings it can read; it cannot see a finding that never reached disk. In run sd-20260919-075508 a review file arrived as the 32-byte literal `{"issue": 2587, "findings": []}` while its `.json.raw` sibling still held four findings — the first a `correctness` defect — and the gate scored it `clean` and the PR merged. The reviewer's reported count was in this conversation's hands the entire time and was discarded. Pass it through: a disagreement is a hard error (exit 3), never a verdict. Do **not** attempt to repair a short file from its `.raw`; salvage is the likeliest cause of the empty file in the first place. Re-run the Review subagent instead.

**Fallback (engine unavailable — `CO_HOME` unset/unbuilt, or the invocation errors):** revert to the pre-C1 path. Cleared count ≥ `--workflow-threshold` **and** `Workflow` available → `Workflow({ scriptPath: "$SD/workflow.js", args: { repo, blockOn, reviewDir: "$STATE/reviews", issues: [{ number, digest, complexity, implEffort, reviewEffort }] } })`. Resolve each issue's `implEffort` from tuning.json before the call — read the map once with `node "$SD/scripts/lib/tuning.mjs" resolve implement` (JSON) and take `map[complexity]`; an issue's own `effort` wins, an issue with no complexity takes `map.normal`, and an issue whose complexity isn't a key of the map is refused, exactly as emit-config refuses it (fix the triage output first) — and pass it explicitly: workflow scripts never read tuning.json, and `workflow.js`'s `implEffortFor` map is only a pinned last resort. Else inline `Agent` fan-out (one Implement per issue in a single message, Review each as it returns). Both blocks are still present and produce the same result shape. The engine is preferred: it actuates per-issue effort literally, isolates per-repo worktrees + CI, and survives `--detach` — the fallback keeps ship-dag working without the engine checkout.

**Mixed-repo waves:** the engine handles them natively (per-issue `repo` → per-repo worktree, base branch, and CI), where `workflow.js` takes a single `repo` per batch. In practice a single ready wave rarely mixes repos, since cross-repo edges fall on wave boundaries where step 7's point-C gate already stops you.

### 5. Reconcile each result

- **The gate exited non-zero — there is no verdict, and that is not a pass.** `review-gate.mjs` reports failure through its exit code, and step 5 must branch on it before reading stdout (which is empty in both cases). **Exit 2** — a malformed invocation (an unknown `--block-on` category, a non-integer `--expect-findings`, a flag with no value): *your* mistake, fix the command and re-run; nothing about the PR is yet known. **Exit 3** — the review file is unreadable or did not arrive intact: unparseable JSON, no `findings` array, or a finding count disagreeing with what the subagent reported writing. Re-run the **Review** subagent for that PR — do not repair the file, do not hand-count the findings, and never fall back to merging on CI alone. If a second review also exits 3, that is **HITL point B**: something is wrong with the reviewer or the state dir, not with the PR. Roughly 1.5% of logged review files are already unreadable (one of 66 is invalid JSON), so this path is live rather than theoretical.
- **Green** — CI pass, gate `verdict` not `blocking`, no open questions → queue for merge. A row whose `ciStatus` is `"none"` because the engine stopped before its check (step 4c's resource stops) is not green yet: run the repo's CI profile first, `node "$SD/scripts/run-ci-profile.mjs" --repo <owner/repo> --worktree <path>` exactly as step 6.2 does (alone in its own Bash call; exit 75 reruns under that step's 15-minute preflight and 30-minute cap, which reach point F; do not restate its loop here), after the resource preflight (step 4) clears. Exit 0 sets `ciStatus: "pass"`, and the row is then green. Exit 64 with `no CI profile` in its stderr leaves `"none"`, and the row goes to the gate as an unverified repo, as step 4c treats a repo with no `postSessionCheck`; any other exit 64 is a setup error to fix before queueing. Any other non-zero exit, including 128 plus a signal number, sets `"fail"`, which follows the non-flaky CI failure rule below (`ciStatusAfterProfile` in `scripts/lib/failure.mjs` is that mapping). Carry `nitCount`, `selfClearedCount`, and `path` into the wave summary; a `nits-only` PR's findings are worth a human's eye, but reading them is *their* call, not a cost the run pays automatically — a non-zero `selfClearedCount` says the reviewer downgraded its own CONFIRMED finding to get here, which is the case most worth their eye.
- **Blocking finding** (`blockingCount > 0`) → Apply step 4d's hand-off limit and its lease-wait routing, with one `/review-loop` invocation's PR set as the hand-off unit. Hand `/review-loop` the PR — `/review-loop owner/repo#PR --max-iter K` (from *you*, the main agent — reliable Skill access) — and quote it the blocking findings from the review `path`. `/review-loop` takes only the ref and `--max-iter`, and its passes write no round file, so the round file after a fix is yours: **when `/review-loop` returns converged, run the Review subagent once more as the next round, `<stem>.r<N>.json` (step 4d), with `{TRIGGER}` = `"review-loop"` and the same `{REPORT_ID}`, and gate it with `review-gate.mjs` exactly as step 4d does.** That is the round `ingest-wave` checks: it expects the trigger `review-loop` on exactly the round after a blocking one, and counts that round as a bounce. This is also where an **unrecognized `category`** lands: `review-gate.mjs` folds it into `blockingCount` whatever its `verdict`, so it never merges as a silent nit; quote `unknownCategories[]` to `/review-loop` so the fix (or the reviewer re-run) targets the right finding. That re-gate passes → queue. It blocks → hand the new round to `/review-loop` again while passes remain under `--max-review-iter` (the re-gate after the next fix is round N+1, trigger `"review-loop"` again), else **HITL point B**. A `/review-loop` report that ends with `orchestrator-stop: lease-wait` is a lease give-up (step 4d): requeue, never point B. `/review-loop` does not converge (and its report does not end in the lease-wait line), or the fix needs a design call → **HITL point B**. On a bounce, the retried implement runs one effort tier higher (rubric guardrail 2).
- **A `succeeded` row with no `prNumber` — route `find-pr`.** The engine only recognises a PR on the branch it checked out, so a session that pushed a self-chosen branch is recorded `succeeded` without one. Look it up: `gh pr list --repo <repo> --state open --search "Closes #N in:body"`. Exactly one match → gate it like any `succeeded` row (step 4d). No match, or more than one → **HITL point B**.
- **Any `failed`/`blocked` row, or `pending` row carrying a `failureReason` — diagnose it in ONE call before deciding anything:**
`node "$SD/scripts/diagnose-failure.mjs" <owner/repo#N> --run-id <runId>` (or `--state-dir <any dir of the run's family>`; **the two are interchangeable, and a suffixed wave dir is never needed**: either finds the ref's owning report across the whole run family and reads the digest and transcript from the dir that report is in, so the dir you pass never picks a wave). It returns `{ status, prNumber, prUrl, exitCode, failureReason, stopStage, ciStatus, route, terminal }` in a few hundred bytes — the row, the rate-limit classification, the engine's stop stage and CI status, the engine's exit code, and the session's terminal `result` record. The engine already wrote that object for every non-succeeded row as the wave finished (`<stateDir>/state/failure-digest/issue-<encoded-ref>.json`, streamed while the transcript was hot); this reads it, and recomputes the same shape from the report and transcript (`source: "report"`, not `"digest"`) for a run that was never digested or whose digest is stamped by a report other than the one `--owner` names, so a `report` source is not a broken digest pass. **Never `cat`/`tail`/`grep` `<stateDir>/state/logs/issue-*.log` yourself**: despite the name those are full stream-json session transcripts, not logs in the skim-me sense — routinely megabytes (1.1MB in sd-20260831-162148) — and pulling one into context costs more than the wave it describes. Act on `route`:
  - `review-gate` — a PR is open, whatever the status says. The implement work landed; gate it like a `succeeded` row (step 4d) and let step 6 merge it; a stop's own `ciStatus` from the digest overrides the "treat as pass" default. **Do not retry**: the branch exists and the work may already be merged.
  - `resource` — no PR, and the engine stopped the row for memory pressure or a lease wait (a `pending` row stopped at `launch`, or a `failed` one). **Infrastructure, not a model failure, and never point B.** Run the resource preflight (step 4) first (wait, then ask at point F). After a ref's second resource stop in a run, go to HITL point F whatever the pressure instead of resuming or re-running it again: the preflight returns `proceed` at every pressure below `critical`, so busy lease slots alone could otherwise repeat the stop forever. A continuation agent that gives up on the lease (its return ends with the closing line `orchestrator-stop: lease-wait`, or on the fallback it returns `status: "error"` with `notes: "lease-wait"`) is not an engine row, so the route counts it itself: it counts as that ref's next resource stop. Otherwise let the worktree decide (`resumeMode` in `scripts/lib/failure.mjs`; `git -C <worktree> log` against the base, and `git -C <worktree> status`): **commits or a dirty tree** → resume in place, as for point E (`references/escalation-policy.md`, "Resource stops"), never re-running the engine for that issue; **a clean worktree with no commits**, whatever the `stopStage` → a filtered re-run: `node "$SD/scripts/lib/wave-spec.mjs" spec.json --wave <label> --state-dir <dir> <ref>... > respec.json`, then `emit-config.mjs` as in step 4a, into its own suffixed state dir (step 4a's suffix rule, for example `<runId>-w<N>b`), with a string wave label such as `"14b"`. Run the engine on that config only: the original config is never re-run, because `prepareIssues` skips only `succeeded` rows and would relaunch every `failed` row into its existing branch. Ingest its report with its own outcomes file. A `pending` row due to be re-run stays not yet terminal; if the user defers the step or stops the run at point F, give it `{"finalState":"deferred"}` (step 6.3).
  - `point-E` — no PR, died on quota. **Infra failure, not a model failure**: ≤2 manual retries, resume-in-place per the point-E recovery recipe in `references/escalation-policy.md` (never re-run the engine for that issue — it would collide with the existing branch; a wait that runs long forks to the point-E grill, not point B).
  - `point-B` — no PR, ordinary implement stall → **HITL point B**. `terminal.reason` is the session's own last word on why; quote it in the grill rather than re-deriving it.
- **Open question surfaced mid-implementation / non-flaky CI failure / judgment-needing merge conflict** → **HITL point B** (grill), then re-queue or defer the issue. A `memory-critical` stop at `retry` is such a failure (`ciStatus: "fail"`): its check ran and failed, so quote the engine's check summary in the grill.
- **Telemetry (non-engine paths only):** on the engine path this wave's step 6.3 records every row from its report, so nothing is hand-written here. On the fallback paths, emit one record for every issue that **terminates here** without merging (`blocked-hitl` / `deferred` / `error`), capturing `implStatus`, `ciStatus`, `reviewVerdict`, `failureReason`, `findings[]`, `bounces`, and `hitl.pointB`. A `"memory-critical"` or `"lease-wait"` stop is recorded the same way, as infrastructure (`implStatus: "error"` beside a death, `null` for a launch stop that never started). A `"rate-limited"` `failureReason` record is emitted here **at death time** regardless of what happens next — even though the issue isn't actually abandoned, it's resumed in place per the recovery recipe (`references/escalation-policy.md`'s point E) and, if the continuation succeeds, gets a *second*, ordinary `merged` record at step 6 for the same issue. `report()` (`scripts/telemetry.mjs`) excludes `"rate-limited"` records from the model-quality indicators so this interim record never dilutes them — see *Telemetry* below.

### 6. Merge queue — auto on green

Side-effecting; all on you, the main agent; serialized in **dependency order**. Per queued PR:

1. `git fetch`; rebase the PR branch onto the latest tip of **its own repo's base branch** — not a hardcoded `main`. Resolve it per repo (`gh repo view owner/repo --json defaultBranchRef -q .defaultBranchRef.name`, or `git rev-parse --abbrev-ref origin/HEAD`); e.g. `wxyc-ios-64` is `master`.
2. **If the rebase moved the base** (a sibling from this wave already merged under it — the normal dependent-wave case): **re-run BOTH local CI and the Opus review gate** — local CI as `node "$SD/scripts/run-ci-profile.mjs" --repo owner/repo --worktree <path>`, alone in its own Bash call. It takes a machine-wide lease slot from claude-orchestrator's `cli-lease.js` for exactly as long as the suite runs, runs each profile command in its own subshell, and exits with the suite's status; set the Bash `timeout` to the suite's budget plus 100 000 ms, capped at 600 000, or background a longer suite. Exit 75 means no slot and is no test failure, so rerun it (a lease rerun is not an infra retry under step 6's ≤2-retry rule), but once the summed waits pass 15 minutes, run `node "$SD/scripts/resource-preflight.mjs" check --waited-minutes <summed wait so far>` first: `proceed` reruns, and `critical-*` goes to HITL point F (wait / start anyway / defer this step / stop the run), where "start anyway" reruns with `CO_PRESSURE_OVERRIDE=critical-as-warning` as an inline prefix on that one command, never exported, when the pressure is `critical`, and plainly below it (the override changes nothing there; the per-step table in `references/escalation-policy.md` has the full row). Because `proceed` comes back at every pressure below `critical`, busy slots alone could keep the reruns going, so once the summed waits pass 30 minutes, whatever the pressure, stop rerunning and go to HITL point F with the same four choices. Exit 64 is a setup error (missing worktree, missing lease CLI, repo with no CI profile): fix the command or environment, because it is never a test failure and never a rerun; anything else, including 128 plus a signal number, is the suite's own result. Then re-check `--block-on` before merging, writing the fresh review as the next round file, `<stem>.r<N>.json` with `{TRIGGER}` = `"rebase"` and the same `{REPORT_ID}`, and passing its `findingCount` as `--expect-findings`, exactly as step 4d does. A verdict computed pre-rebase does not carry over once the base changed, and neither does the arrival check: this is the last gate before `gh pr merge`, so a second review file landing short here is the original hazard at the worst possible moment. If the re-gate now finds a blocking issue, pull the PR back into step 5.
3. `gh pr merge --rebase`.
4. `/cleanup owner/repo#PR` — remove the worktree, delete the branch, fast-forward, prune.
5. **Telemetry (non-engine paths only; an engine wave's merges are recorded by 6.3):** emit one record (`finalState:"merged"`, plus the **worst** `reviewVerdict` seen for the issue — a bounced-then-merged issue logs `blocking`, not the post-fix `clean`, so triage-miss and review-catch stay measurable rather than survivor-biased — `bounces`, and `path`) for the merged issue — see *Telemetry* below.
6. Append the merged issue's ref and PR number to `U`, the run's unretrospected-merge list — the input to step 6.5.

**Never loop-retry a failing CI or merge.** ≤2 manual retries on an infra failure, then stop and surface the failure + cost. No `while`-loops against a red run (rerunning after a `lease: no slot` denial is not an infra-failure retry; the two-denial give-up bounds it). The two-denial give-up applies to hook denials in engine sessions and subagents; the main agent's `run-ci-profile.mjs` exit 75 in step 6.2 is bounded instead by that step's 15-minute preflight and its 30-minute cap, which goes to point F whatever the pressure.

### 6.3 Ingest the wave

After step 6's per-PR list and before 6.5, run it **once per engine report**, **including a report in which nothing reached the queue**, since its skipped, failed and blocked rows are records too. A wave usually has one report, but each engine invocation writes its own: a retry in a suffixed dir, or a `--retry-failed` run, adds another, and each report is ingested with its own outcomes file.

First write the outcomes file, then ingest:

`node "$SD/scripts/telemetry.mjs" ingest-wave <stateDir>/state/reports/<reportId>.json --outcomes "@$STATE/outcomes/<reportId>.json"`

`ingest-wave` derives every row's record from the report, the wave's sidecar entry (else its config), the failure digests, the review rounds and the transcript, and appends the ones the log lacks; never hand-write them. What it cannot see is what happened after the engine stopped, which you supply as `--outcomes`, a JSON object keyed by ref. **Always save it to `$STATE/outcomes/<reportId>.json` before the run** (`mkdir -p "$STATE/outcomes"` first; `<reportId>` is the report's filename stem), as `{}` when no row needs an outcome, so the file exists for every report 6.3 ingested, and every run on that report, now or later, passes `--outcomes @` that file. A missing file makes `ingest-wave` exit 2 with the file's `ENOENT` and no ref named, so never point `--outcomes` at a file you have not written (step 7 says how to rebuild one). Re-running with the same outcomes is a no-op for records already in the log; without them, `ingest-wave` exits 2 for any report with a find-pr row or a PR whose last round blocks, even when every row is recorded.

| Situation | Outcome for `<ref>` |
|---|---|
| A find-pr row whose PR step 5 found | `{"<ref>":{"pr":N}}` |
| A find-pr row point B left without a PR | `{"<ref>":{"finalState":"blocked-hitl","hitl":{"pointB":true}}}` |
| A PR whose last round blocks and that went to point B | `{"<ref>":{"finalState":"blocked-hitl","hitl":{"pointB":true}}}` |
| A PR whose last round blocks and that merged after a `/review-loop` fix whose round file is missing | `{"<ref>":{"finalState":"merged","bounces":N}}` |
| A find-pr row whose found PR's last round blocks | `{"<ref>":{"pr":N,"finalState":"blocked-hitl","hitl":{"pointB":true}}}`, or `{"<ref>":{"pr":N,"finalState":"merged","bounces":N}}` when it merged |
| A rate-limit death that point E resumed | `{"<ref>":{"pr":N}}` for the continuation's PR, or `{"<ref>":{"finalState":"blocked-hitl","hitl":{"pointB":true}}}` when the continuation stalled at point B without a PR; `ingest-wave` then records the death and the continuation separately (`references/escalation-policy.md`, point E). A continuation that finishes after this report's 6.3 ran: add this outcome to `$STATE/outcomes/<reportId>.json` and re-run 6.3 on the report, which appends only the continuation |
| A `lease-wait` or `memory-critical` row (no PR) that step 5's `resource` route resumed in place | `{"<ref>":{"pr":N}}` for the continuation's PR, or `{"<ref>":{"finalState":"blocked-hitl","hitl":{"pointB":true}}}` when it stalled at point B without a PR, as for a rate-limit death; `ingest-wave` records the stop as a deferred death and the continuation separately. Add the outcome to `$STATE/outcomes/<reportId>.json` and re-run 6.3 when the continuation finishes later |
| A stopped `pending` row (`memory-critical` at `launch`) the user deferred at point F or the run stopped on | `{"<ref>":{"finalState":"deferred"}}`; with no outcome the row is not yet terminal and gets no record |
| An engine invocation the user started anyway at point F | `{"<ref>":{"pressureOverride":true}}` for every row of that engine invocation's report (merge it into the row's other fields where one applies); for a filtered re-run, only in that re-run report's outcomes file |

**One ref has one outcome object.** When more than one row of the table applies to a ref (a find-pr row, or a point-E continuation, whose PR's last round blocks), merge their fields into that one object, as the table's fifth row does: given only `pr`, ingest exits 2 for the blocking last round, and given only `finalState: "merged"`, it exits 2 because a merge needs a PR. `bounces` is a floor: ingest records the larger of it and the bounces it counts in the round files, so `0` is safe when you do not know the count.

The `--outcomes` fields are `pr`, `finalState` (`merged|blocked-hitl|deferred|error`), `bounces`, `findings`, `tokens`, `pressureOverride` (`true` only; omit it otherwise) and `hitl.pointB`; `pr` is a positive integer and must be the report row's PR where it has one.

Exit codes: **2** — a bad invocation or `--outcomes` (including a missing outcomes file), or a half-supplied report; read the message, supply the named refs' outcomes, save the file again and re-run. **3** — a malformed report (or no run id); name it in the wave summary and move on. Any other failure is best-effort: say so in the wave summary and continue.

### 6.5 Retrospective — HITL point D

Per-PR review is structurally blind to cross-PR problems: parallel implementers in separate worktrees cannot see each other's work, and the plan's remaining specs were written before this wave's code existed. This pass looks at the run holistically — after the merge queue, before advancing.

**Trigger:** skip unless `|U| ≥ --retro-threshold` (default 3 merged PRs; print the carry-forward count when skipping). **Always run once at drain** — when step 7's stop condition is met with `|U| > 0` — regardless of threshold. `--no-retro` disables both. A pass consumes `U` (reset to empty) whatever it finds, and emits one `kind:"retro"` telemetry record.

**Fan out ONE `Agent{model:"opus"}`** (read-only; the Retrospective block below — this block has exactly one copy, here) with: the merged issue refs + PR numbers in `U`, rendered as `owner/repo#N (PR #M)` pairs so `gh pr diff` has the PR number (all repos); the remaining DAG (`nodes[]` refs+titles and `edges[]` from the current spec, **minus every issue merged this run** — the spec predates this wave's merges, so without the subtraction the plan pass would audit just-shipped issues as pending); the run's issue-set form (epic / label / explicit set); and the run ledger (previously filed retro-ticket refs, previously declined proposals). Hand it `{RETRO_PATH}` = `$STATE/retro/wave-<W>.json` (`mkdir -p "$STATE/retro"` first). It writes the full `references/retrospective-schema.md` envelope there — `{ mergedPrs, refactors[], planAdjustments[], observations[] }` — and returns that same envelope **minus every `body` and `proposal`**, the two long fields, plus a stable `id` per proposal. That is exactly what point D's checkboxes need; the drafted text is only needed for proposals the human actually approves, and most are declined. The main agent stamps `wave: W` when emitting the telemetry record; the subagent never produces it.

**HITL point D** (protocol in `references/escalation-policy.md`): if `refactors` and `planAdjustments` are both empty, print `observations` in the wave summary and move on — no grilling. Otherwise **batch everything into one grilling**, mirroring point A:

1. Present refactors via `AskUserQuestion` with `multiSelect` — one option per proposal (title + one-line summary + evidence PR refs), recommended-first; ≤4 options per question, paginate if more. Plan adjustments likewise; an open-ended `respec` gets the inline grill-me-style interview instead of a checkbox.
2. **Approved refactors** → fetch each approved proposal's drafted text one at a time, by id: `node "$SD/scripts/retro-pick.mjs" "$STATE/retro/wave-<W>.json" R1`. Never read the whole retro file back — the declined proposals' bodies are the bulk of it and nothing needs them. Then ghost-write one ticket each via `/file-ticket`, **in the refactor's `repo`** — never the cwd default, which on a multi-repo run may contain none of the code (the drafted `body`; the `complexity` tier as triage context) — then insert into the run's DAG by issue-set form: **epic run** — attach as a native sub-issue of the epic (GitHub allows a cross-repo sub-issue; if it refuses the attach, the ticket instead gets a prose `## Related` link to the epic AND is appended to the in-context set explicitly); **`--label L` run** — apply label `L` to the new issue; **explicit-set run** — append the fully-qualified `owner/repo#N` to the in-context issue set. Encode each approved `blockedBy`/`blocks` edge **both ways** so step 1's two merged edge sources pick it up: the native dependency graph AND body prose (`Blocked by owner/repo#N`). A refactor whose implementation consumes another repo's just-merged artifact must also carry a `Blocked by` edge naming that **merged** upstream issue — fetch folds it straight into `done[]`, so it never blocks, but the cross-repo edge is what routes the ticket through step 7's point-C cutover gate instead of letting it auto-release against an unpublished artifact.
3. **Approved plan adjustments** → ghost-written issue comments recording the decision and reasoning; body edits where the spec changed (`respec`); native edge add/remove plus matching body-prose edit (`add-edge`/`drop-edge`); `gh issue close --reason "not planned"` with an explanatory comment (`obsolete` — the one destructive act: confirm it individually in the grilling, never inside a multiSelect batch); `split` files children via `/file-ticket` and respecs the parent.
4. **Declined proposals** → recorded in the run ledger only; nothing written to GitHub; never re-proposed this run.
5. Filed tickets flow into the next step-1 fetch and ship through the normal triage→implement→review pipeline — the retro itself never writes code and never merges.
6. **If the just-filed tickets are the only thing keeping the run alive** — this pass ran in drain mode, *or* it ran at threshold on what would otherwise be the run's final wave (ignoring the tickets it just filed, step 7's stop condition would hold) — ask one final crisp fork: ship them **in this run** (run step 7 for the wave just finished, which closes its sub-epic on an epic run, then loop back to step 1) or **leave them filed** for a future `/ship-dag` invocation (run ends). Filing tickets must never silently extend a run that was about to end; this question is the loop's termination valve.

**Telemetry:** emit one `kind:"retro"` record per pass — `{ kind:"retro", runId, wave: W, mergedPrs, proposedRefactors, approvedRefactors, declinedRefactors, proposedAdjustments, approvedAdjustments, declinedAdjustments, filed[], adjusted[], declinedTitles[] }` (see *Telemetry* below; `declinedTitles` persists the declined half of the ledger — titles only — so a resumed run can rebuild it, with point D backstopping near-duplicate re-proposals the title match misses).

### 7. Advance — HITL point C on any cross-repo cutover, point D on any tripped tripwire

Mark merged issues done. **On an epic run, close the wave's sub-epic** (if step 3c opened one): `node "$SD/scripts/wave-epic.mjs" close --repo <epic repo> --epic N --wave-epic <number> --outcomes @<file>`, where the file maps each wave ref (`owner/repo#N`, `#N` or `N`) to `{ finalState, failureReason?, pr? }`. Every still-open issue under the sub-epic (blocked-hitl at point B, error, rate-limited) goes back to the epic, decided from live state, not from the file, which only fills the comment's PR and note columns; one comment records the per-issue table; and the sub-epic closes. It refuses (exit 2, before any write) an issue that isn't a `ship-dag-wave` sub-issue of the epic, a `--wave-epic` gh cannot find ("could not be read"), or an outcomes key that isn't an issue ref. Exit 1 with `stuck[]` means a return failed: the sub-epic is left open on purpose (the fetch still ships what is under it, and the next wave's `open` takes those issues into its own sub-epic) — report the stuck refs in the wave summary. Exit 1 without JSON means a GitHub call failed partway: run it again. **Run `audit` before going to step 1:** `node "$SD/scripts/telemetry.mjs" audit "$RUN_ID"` prints `{runId, dirs, notIngested: [{dir, id, source, refs}], unreadable: [{path, error}], neverReported: {sidecar: [{dir, refs}], configs: [path]}}`. It exits 2 on a usage error and 1 on any other error, with the reason on stderr after `audit: `. Exit 1 is benign only when stderr starts with `audit: no dir under` (no engine dir belongs to the run) **and** the run has had no engine wave, because every wave took a fallback path: say so and move on. Any other exit 1 is a failure, not an all clear: an unreadable telemetry log, an engine base dir that cannot be listed, or `no dir under` on a run that did run an engine wave (a wrong id; recover it as step 1 does for a resume). Name it in the wave summary. `audit` reads each row's failure digest through the same wave window as ingest, so never delete, move or copy a run's `state/` digests before `audit` and `ingest-wave` have run on it (a digest or review round stamped with its report id is windowed by that id, but an unstamped digest, written before #161, and an unstamped round, written before #169, are windowed by mtime, so a copy that does not keep mtimes changes both verdicts for those; a ref's rounds are ordered by their `.r<N>` number, but by mtime when any of them is named another way, so such a copy can reorder those rounds too). Act on each class:

- `notIngested` — run 6.3's `ingest-wave` on `<dir>/state/reports/<id>.json` with `--outcomes "@$STATE/outcomes/<id>.json"`. If that file does not exist, the report's 6.3 never ran: rebuild its outcomes from 6.3's table, save them to that path (as `{}` when no row needs one), then ingest. For a find-pr row, run step 5's find-pr lookup with `--state all` instead of `--state open`, since the PR may have merged or closed since. For a PR whose last round blocks (the find-pr row's found PR included), run `gh pr view <PR> --json state`: `MERGED` gives `{"finalState":"merged","bounces":N}`, and `OPEN` or `CLOSED` (closed without merging, after point B) gives `{"finalState":"blocked-hitl","hitl":{"pointB":true}}`. For `bounces`, use the number of `/review-loop` fix passes when the wave summary or the PR's history shows it, else `0`: it is a floor (6.3), so ingest still counts the bounces the round files show. For a rate-limit death that point E resumed, the continuation's PR (`gh pr list --repo <repo> --state all --search "Closes #N in:body"`) gives `{"pr":N}`; with none, `{"finalState":"blocked-hitl","hitl":{"pointB":true}}` if it went to point B, else no entry, so ingest records the death alone. Merge the fields of one ref into one object, as 6.3 says. An exit 2 that names refs means a row still lacks its outcome: add it to the file and re-run.
- `unreadable` — name it in the wave summary, as for `ingest-wave`'s exit 3.
- `neverReported` — no report exists, so there is nothing to ingest: **never ingest or hand-write records for it.** At step 7 it is an earlier emit of a ref set that was emitted again, or a wave the engine died in before it wrote a report. At a resume it can be the wave that was in flight, and that wave can still be running. Check before you report it as dead, against this dir's engine only. `pgrep -f 'scripts/engine/run.mts'` lists every run's engines, since the config path rides in the `SHIP_DAG_CONFIG` environment variable, not in the arguments, so a bare hit says nothing about this wave. Match the environment instead: `for p in $(pgrep -f 'scripts/engine/run.mts'); do ps -Eww -o pid=,command= -p "$p" | grep -F "SHIP_DAG_CONFIG=<dir>/"; done` (macOS `ps -E`; on Linux, `grep -z` on `/proc/$p/environ`). `<dir>` is the sidecar entry's `dir`, or the `configs` path's directory, and the trailing `/` keeps `<dir>` from matching `<dir>-w2`. A hit is this dir's engine, a `--detach` child too, since the child inherits the environment. The `npm exec` wrapper rewrites its process title and so shows no environment, but its `tsx` and `node` children do. Then `ls -lt <dir>/state/logs/ | head -3` shows whether its transcripts are still being written (compare their mtimes with the current time; list them, never read them). Whether to re-run it is the human's decision.
- If a re-ingest with the saved `--outcomes` appends nothing and `audit` still names the wave, it is one of two known cases: the row's only record is a hand-written PR-less failure from before the report started, or the row is covered under another `finalState` (a point-B hold of its PR, or an operator's `deferred`) or is a PR-less row whose PR came from `--outcomes`. Name the row once in the wave summary and move on; never hand-write a record to clear it.

**Tripwires:** after `audit`, run `node "$SD/scripts/telemetry.mjs" tripwires [--escapes "$STATE/escapes.json"]`, passing `--escapes` only when that file holds valid JSON. It prints one result per tuning tripwire in `references/tripwires.json` (state, sample, any `reviewOverdue` date, and the proposed action) and exits 2 on a usage error and 1 on any other error, with the reason on stderr after `tripwires: `. It is best-effort: on a non-zero exit, name the failure in the wave summary and go on, never abort the wave. T-escapes needs a saved `escapes` run, and without `--escapes` it reports `insufficient-data` with a hint on every wave. `escapes` searches GitHub, so run it once per run and have every later wave pass the saved file. Run it whenever `$STATE/escapes.json` is missing, empty or not valid JSON (`node -e 'JSON.parse(require("fs").readFileSync(process.argv[1], "utf8"))' "$STATE/escapes.json" 2>/dev/null` exits non-zero), through a temp file that moves into place only on exit 0: `node "$SD/scripts/telemetry.mjs" escapes > "$STATE/escapes.json.tmp" && mv "$STATE/escapes.json.tmp" "$STATE/escapes.json"`. A redirect straight to `escapes.json` leaves an empty file when `escapes` fails, and `tripwires --escapes` then exits 1 on every later wave. On a failed `escapes`, name it in the wave summary, run `tripwires` without `--escapes`, and retry `escapes` on the next wave. `escapes` exits 0 when GitHub fails for some PRs or issues, skipping each with a warning, so a run during a GitHub outage saves a short population. Two warnings mean a GitHub call failed: `skipped owner/repo#N` (a PR view) and `owner/repo#N: closing PRs not found; skipped` (the closing-PR lookup). When stderr holds either, say so in the wave summary, and delete `$STATE/escapes.json` to have the next wave run it again. Its other `skipped` warnings (an unreadable report, a ref that is not `owner/repo#N`, an issue that no single merged `orchestrator/` PR closes) come back on every run, so they never call for a re-run. T-coverage runs `audit` itself, for each run family with a current-version record after its `since`. Put every `tripped` tripwire and every `reviewOverdue` in the wave summary and answer them at HITL point D (`references/escalation-policy.md`) in one grilling of their own, held here in step 7 after `tripwires` prints. It never joins step 6.5's grilling: in a normal wave that grilling has ended before step 7 runs. Each one is answered **confirm offline** (the eval or analysis the action names), **retune** (change `references/tuning.json` or the decision, and recompute the baseline when the cause is a definition change in `references/decisions.md`'s *Metric definitions*), or **dismiss with a reason**. Log a dismissal under *Dismissals* in `references/decisions.md`, with the evidence, so the same evidence is not proposed again. When a `reviewOverdue` is answered, move the review date to the answer date + 60 days (`date -j -v+60d +%Y-%m-%d` on macOS, `date -d '+60 days' +%F` on Linux), in the same commit, in both places: the *Review date* of the decision's entry in `references/decisions.md`, and the `reviewDate` of every row in `references/tripwires.json` whose `decision` names that entry (a row whose `decision` is `all` names the entry of its own id, under *Cross-cutting tripwires*). A date left in the past makes every later wave report the review overdue again and raise point D for it. Nothing retunes itself.

**Point C telemetry:** a cross-repo cutover deferral at this step is hand-written (see *Telemetry*). Then go to step 1. The re-fetched `done[]` will surface the next wave.

**Cross-repo cutover gate — "satisfied" ≠ "merged" across a repo boundary.** A merged upstream PR is not consumable downstream until it is published/deployed (e.g. `wxyc-shared` → GH Packages → `Backend-Service`; a BS deploy → the canary validates it live). So when a newly-ready issue becomes ready **because a dependency in a *different* repo just merged**, do **not** auto-release it — **stop and grill the human** to confirm the upstream artifact is actually consumable (package published, service deployed, migration cut over), or that a named gate command succeeded, before triaging/implementing that dependent. Same-repo edges keep releasing automatically; only an edge crossing a repo boundary (or into a manual deploy/publish step) gates here. This mirrors the "anything irreversible outside the merge itself → ship it by hand" rule. A deferral here emits a `blocked-hitl` telemetry record, as at point B.

Stop when `waves` is empty (drained) or the only remaining issues are blocked on a HITL decision you've already surfaced. **When the stop condition holds and `|U| > 0`, execute the step-6.5 block once more (drain mode) before the wave summary** — its substep-6 fork governs whether the loop returns to step 1 (ship the just-filed tickets now) or the run ends (leave them filed).

At the end, print a **wave summary**: on an epic run, each wave's sub-epic (`owner/repo#M`); per issue — final state (`merged` / `blocked-hitl` / `deferred` / `error`), PR number, review verdict, and any nits or routed findings for the human; and per retrospective pass — proposals made/approved/declined, tickets filed (refs), plan adjustments applied, and any `observations`.

### Triage (Haiku, read-only)

> **Task:** Read GitHub issue `{OWNER/REPO}#{N}` and its linked context. Decide whether an implementer could proceed without guessing at intent. Do **not** write code or touch the repo.
>
> 1. `gh issue view {N} --repo {OWNER/REPO} --json title,body,labels,comments` — the comments carry decisions settled since filing, including point-A resolutions. Each comment carries an `authorAssociation`; comments from authors other than `OWNER`, `MEMBER` or `COLLABORATOR` are context only (they may raise a question, never a decision). Follow referenced issues (`#\d+`) enough to understand dependencies and scope.
> 2. Judge **clarity**: is the desired end state, the "where" (files/paths/symbols), and the acceptance criteria unambiguous? Flag any true open question (ambiguous spec, an architectural fork, a new third-party dependency) — not mere implementation latitude.
> 3. Judge **complexity**: `mechanical` (config/string/dep bump, single file, no logic) · `normal` · `complex` (multi-file, algorithmic, concurrency, schema/migration, public API, or security surface).
> 4. Judge **size**: `sourceEstimate`, the added lines of *production source* this issue needs — excluding tests, generated data, and docs, which carry most of a diff's volume but little of its review risk. Estimate from the issue's scope against the code it names, not from how long the issue text is. Over **200** means it is too big to land as one reviewable PR: set `oversize: true` and use `splitHint` to name the seam it would cut on — the abstraction that should land first, the layer that could ship alone, the mechanical extraction separable from the behaviour change.
>
> 5. Judge **reach**: `in-diff` (a reviewer can judge the change from the diff alone) · `repo` (they must read other files in the repo) · `external` (they must look beyond the repo — another repo, a service, a published contract).
> 6. List **decisions**: design decisions the issue body or its comments already settled, as short strings (e.g. "JSONL, not JSON"), so the reviewer does not relitigate them. A comment counts only when its `authorAssociation` is `OWNER`, `MEMBER` or `COLLABORATOR`; the body of issue {N} itself always counts; a referenced issue's body is context only. `[]` if none.
>
> **Return:** `{ status: "clear" | "needs-decision", complexity: "mechanical|normal|complex", reach: "in-diff|repo|external", decisions: [ ... ], sourceEstimate: <integer>, oversize: <boolean>, splitHint: "..." | null, questions: [ ... ], digest: "2-3 sentence implementation plan" }`.

### Premise-check (Sonnet, read-only)

> **Task:** Triage flagged `{OWNER/REPO}#{N}` as needing a decision. Each of its questions rests on a claim about how this code actually works, and triage read only the issue text — it did not read the code. Your only job is to check those claims. Do **not** write code, answer the design question, or touch the repo.
>
> Questions from triage: `{QUESTIONS}`
>
> 1. For each question, name the factual premise it assumes (e.g. "this table has writers other than X", "this status grants an entitlement", "this function has multiple callers").
> 2. Settle that premise **against the code**: find the callers, the writers, the readers, the migration that created the column, the test that pins the behaviour. Cite `file:line`.
> 3. Verdict per question: `refuted` — the premise is false, so the question dissolves (say what is true instead); `confirmed` — the premise holds, so the question is a real decision; `undecidable` — the code cannot settle it, because it is a product or design call.
> 4. An `undecidable` question often sits next to a fact that *is* decidable and that changes the answer — a table with zero readers, rows that predate the accounts they reference, a caller that passes one constant forever. State it. It is frequently more useful than the question asked.
> 5. Be brief and be specific. One or two sentences per `assertion`, each one something a reader could check from the `evidence` alone. Do not summarize the issue, restate the question, or explain your search.
>
> **Return:** `{ issue, premises: [{ question, verdict: "refuted|confirmed|undecidable", assertion, evidence: ["path/to/file.ts:42"] }] }`. No Claude/AI mention anywhere.

### Implement (Sonnet, own worktree)

> **Task:** Implement `{OWNER/REPO}#{N}` in a fresh, disposable git worktree. Digest from triage: `{DIGEST}`.
>
> 1. Locate the repo checkout (sibling under `/Users/me/Developer/`, else `gh repo clone`). `cd` in. Read repo + package `CLAUDE.md` and the patterns in the module you're touching; match them.
> 2. Test-first: failing test → smallest correct implementation → passing test. No drive-by refactors — every extra change is something the review will flag.
> 3. Run the repo's local CI (lint/format/typecheck/tests, or `npm run ci:*`). Fix red before pushing; never push known-red to bait the review. Heavy commands are leased machine-wide by a hook; one may wait several minutes before it starts, which is expected. Run heavy commands in the foreground (the hook refuses background ones). A denial reading `lease: no slot after <n>s` means rerun the same command; it is never a test failure and never a reason to skip CI. Claude Code prefixes the denial, so the tool result may read `PreToolUse:Bash hook error: lease: no slot after 450s …`; a tool result containing `lease: no slot after` anywhere, even one prefixed "hook error", means the lease is busy, not that the hook is broken, so rerun the same command. Rerun once. After the second `lease: no slot` denial in the session, whichever commands they hit, stop: comment on the issue, end your final message with the exact line `orchestrator-stop: lease-wait`, and exit without pushing. Never wrap a command in `cli-lease.js` yourself, and run `cli-lease.js` or `run-ci-profile.mjs` alone in its own Bash call.
> 4. **Size check — run it as you work, and again before you commit.** Your budget is the one stated in the digest above, or **200 added lines of production source** if it names none. Tests, generated data, and docs sit *outside* the budget and must never be trimmed to fit it. Measure with `git diff --stat "$(git merge-base HEAD "origin/$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name)")"` and count only the source files. Within budget, or over by less than half → carry on. **Over by more than half → stop and cut**: take the change back to the last point where the tests pass and the slice stands on its own, push *that*, and record the remainder — what you left undone and the seam you cut on — under a `## Deferred` heading in the PR body and in `splitRemainder`. A narrow PR that lands beats a complete one that stalls in review; the retrospective files the remainder as its own ticket.
> 5. Commit (**ghost-writer: no Claude/AI attribution anywhere**), push a dedicated branch, open a PR whose body contains `Closes #{N}` and cross-references the issue.
> 6. **If you hit a genuine open question mid-implementation** that the issue + repo conventions don't answer, STOP: return `status: "blocked"` with the questions — do **not** push a guess.
>
> **Return:** `{ issue, status: "pushed|blocked|error", branch, pr, ciStatus: "pass|fail|none", openQuestions: [ ... ], splitRemainder: "..." | null, notes }`. If you gave up on the lease (`orchestrator-stop: lease-wait`), return `status: "error"` with `notes: "lease-wait"`.

### Review (Opus, own worktree)

> **Task:** You are the last code-review gate before `{OWNER/REPO}#{N}` (PR `#{PR}`, branch `{BRANCH}`) reaches its base branch. Nothing downstream catches your misses — reason exhaustively.
>
> 1. In your worktree: `cd` into the checkout, `git fetch`, `gh pr checkout {PR}` (or check out `{BRANCH}`).
> 2. Review the PR against **its own base branch** (`git diff origin/$(gh pr view {PR} --json baseRefName -q .baseRefName)...HEAD`, or simply `gh pr diff {PR}`) — do not assume `main`; this repo's base may be `master`. Cover correctness, security, simplification, efficiency, test coverage, convention, and contract.
> 3. Optionally, if the Skill tool is reachable, also run the built-in `/code-review` and union its findings. If not reachable, your inline review stands alone. Heavy commands are leased machine-wide by a hook; one may wait several minutes before it starts, which is expected. Run heavy commands in the foreground (the hook refuses background ones). A denial reading `lease: no slot after <n>s` means rerun the same command; it is never a test failure and never a reason to skip CI. Claude Code prefixes the denial, so the tool result may read `PreToolUse:Bash hook error: lease: no slot after 450s …`; a tool result containing `lease: no slot after` anywhere, even one prefixed "hook error", means the lease is busy, not that the hook is broken, so rerun the same command. Rerun once. After the second `lease: no slot` denial in the session, whichever commands they hit, stop: comment on the issue, end your final message with the exact line `orchestrator-stop: lease-wait`, and exit without pushing. Never wrap a command in `cli-lease.js` yourself, and run `cli-lease.js` or `run-ci-profile.mjs` alone in its own Bash call.
> 4. Classify **each finding** per `references/review-schema.md` — `category`, **exactly one of `correctness | security | simplification | efficiency | test-coverage | convention | contract`**, `verdict: CONFIRMED | PLAUSIBLE`, and `blocking: true | false` — your own call on whether *this specific finding*, not just its category, should block the merge (e.g. two `test-coverage` findings in one review can differ: a test that cannot fail in the direction it exists for is `blocking: true`; a documentary case is `blocking: false`). Any other category (or a blank one) fails the gate closed and bounces the PR to `/review-loop`, which has no fix for a taxonomy error — so pick the nearest listed category rather than coining one. Do **not** decide the overall gate yourself: `scripts/review-gate.mjs` recomputes it from your findings, so a merge never turns on a model's claim about its own output — `blocking` narrows which findings in an already-blocking category count, it can never clear one on its own, and omitting it fails toward blocking.
> 5. **Write the full schema object to `{REVIEW_PATH}`** — `{ issue, meta: { trigger: "{TRIGGER}", reportId: "{REPORT_ID}" }, findings: [{ category, verdict, blocking, file, line, summary, failure_scenario }] }` — and return only the summary below. Your findings are read from that file at the moment they're actually needed (a `/review-loop` route, or a report to the human); returning them inline instead would park every one of them in the orchestrator's context for the rest of the run.
>
> **Return:** `{ issue, path: "{REVIEW_PATH}", findingCount, headline }` — `headline` being one line naming the most serious finding, or `"no findings"`. **`findingCount` is cross-checked against the file you wrote and must equal the number of entries in its `findings[]`**: the gate is re-run with your count and refuses to score the review if the two disagree, so an inaccurate count stalls the PR rather than flattering it. Count what you wrote, not what you intended to write. If you gave up on the lease (`orchestrator-stop: lease-wait`), write no review file and delete a partial one you started. If you gave up on the lease, return only the closing line `orchestrator-stop: lease-wait` instead of the summary. No Claude/AI mention anywhere.

### Retrospective (Opus, read-only)

> **Task:** You are the retrospective pass for this run — per-PR review sees one PR at a time; you see the run as a whole. Nothing downstream re-examines the merged surface — reason exhaustively across it. Since the last retrospective these PRs merged: `{MERGED_PRS}` (pairs of composite issue ref and PR number, `owner/repo#N (PR #M)`, possibly spanning repos — the PR number is what `gh pr diff` takes). The remaining DAG is `{REMAINING_NODES}` (refs + titles) with edges `{REMAINING_EDGES}`. Already filed by earlier retrospectives: `{FILED_REFS}`. Previously declined by the human — do **not** re-propose these or trivial variants: `{DECLINED}`. Do not write code, comment on issues, or modify anything — you propose; the human disposes.
>
> 1. Read each merged PR's diff against its own base: `gh pr diff {PR} --repo {OWNER/REPO}` and `gh pr view {PR} --repo {OWNER/REPO} --json title,body,files`. For the plan pass, read each remaining node's spec: `gh issue view {N} --repo {OWNER/REPO} --json title,body,labels`. Work from diffs; open files at the merged tip (sibling checkout under the org root) only where a diff alone is ambiguous. No worktrees, no checkouts of your own.
> 2. **Cross-PR pass:** over the union of the diffs, find what per-PR review structurally misses — near-duplicate logic landed by parallel implementers, the same problem solved two ways (pattern divergence), extract-helper/shared-module opportunities, duplicated test fixtures or setup. A cross-PR finding must cite **≥2 merged PRs** as evidence, at least one not itself a retro-filed ticket's PR (no refactors of refactors); a single-PR finding belongs to the review gate that already ran — drop it.
> 3. **Plan pass:** reread each remaining node's spec against what actually merged. Flag: a stale spec (merged code changed the ground it assumed — `respec`), a wrong or missing dependency (`add-edge` / `drop-edge`), an issue whose work already landed incidentally (`obsolete`), an issue the merged reality has made too big (`split`). A merged PR body carrying a `## Deferred` heading is an implementer telling you it cut itself short against its line budget: the remainder named there is a `split` proposal with the evidence already written — draft it as a ticket rather than re-deriving it from the diff. Propose the smallest edit that makes the plan true again, with the evidence PR(s).
> 4. For each refactor: classify with the review vocabulary (`category` from the finding schema; confidence `CONFIRMED | PLAUSIBLE`), assign a `complexity` tier (`mechanical|normal|complex` — it sets implement effort if the ticket ships), name the `repo` the ticket belongs in (the run may span repos; the ticket's home is where its code lives, not where the run started), suggest `blockedBy`/`blocks` edges against remaining nodes where ordering matters — plus an edge naming a **merged** upstream in a *different* repo whose artifact the refactor consumes (it never blocks, but it routes the ticket through the cross-repo cutover gate) — and draft a ticket `body` to the `/file-ticket` bar: problem, desired end state, where (files/symbols from the evidence), acceptance criteria, evidence PRs as context links.
> 5. Rank refactors by expected payoff and keep the list short (≤5 typical) — a laundry list buries the two that matter. Anything real but not worth a ticket goes in `observations`. Nothing you return gates a merge; everything you saw already shipped.
>
> 6. Give every proposal a stable `id` — `R1, R2, …` for refactors, `P1, P2, …` for plan adjustments, in the ranked order of step 5. **Write the full envelope to `{RETRO_PATH}`**, then return that envelope with each proposal's `body` (refactors) and `proposal` (plan adjustments) **omitted**. Those two fields are long, and only the proposals the human approves ever need them — they are fetched back by id from the file. Everything else stays in the return: point D's grilling renders from titles, summaries, evidence and edges.
>
> **Return** the retrospective schema (`references/retrospective-schema.md`) minus the drafted text: `{ path, mergedPrs, refactors[{ id, title, repo, category, confidence, summary, locations, evidence, complexity, suggestedEdges }], planAdjustments[{ id, ref, kind, rationale, evidence, edge }], observations[] }`. No Claude/AI mention anywhere.

## Model & effort

Per-step model and effort defaults, the complexity→effort mapping, and the "never crank effort on a weak model" / "escalate on failure per item" guardrails live in `references/model-effort-matrix.md`. Effort is actuated **literally** on the two primary paths — the engine (implement sessions: per-issue `model`/`effort`/`complexity` in the emitted config → `--model`/`--effort` on each session) and `workflow.js` (`agent(prompt, { effort })`, implement and review both); the inline `Agent` fan-out — the fallback, the engine-path review gate, and the retrospective always — approximates it via model choice + prompt framing.

## Telemetry

Every issue that reaches a terminal-for-this-wave state emits one JSON record — and every retrospective pass emits one run-scoped record — to an append-only run log, so leading indicators — Sonnet first-pass yield, triage-miss rate, review bounce/catch, HITL frequency, retro proposal/approval volume — are tracked across runs nearly for free. On the engine path the records are not hand-written: **step 6.3** runs `ingest-wave` once per engine report (a retry dir or a `--retry-failed` run adds a second report to a wave) and derives every row's record from the engine's artifacts, and `audit` (step 7, and step 1 of a resumed session) finds a wave whose ingest never ran. Four points stay hand-written: **step 3**'s point-A defer, **step 6.5** (one retro record per pass), **step 7**'s point-C deferral, and the non-engine paths (the `workflow` and `inline` fallbacks, whose step 5 and 6 emissions are written by hand). A hand-written record writes `pr` as a positive integer (older `owner/repo#N` and PR-URL spellings are still read, but a new record writes only the number).

- **Append** (best-effort — a telemetry failure must never abort a wave): `node "$SD/scripts/telemetry.mjs" append '<json>'` (or `@file` / `-` for stdin). The record is validated and `ts`-stamped on write. Schema: `{ runId, repo, issue, complexity, triageStatus, assignment, path, implStatus, ciStatus, reviewVerdict, failureReason, findings[], reviewPath, bounces, hitl:{pointA,pointB}, finalState, pr, tokens, tuningVersion }`; `findings[]` carries the gate's `blocking[]` summary (≤3 one-liners) rather than the full set, and `reviewPath` points at the review file holding all of them — the complete findings are never lost, they just stop being re-ingested to be logged; `implStatus`/`ciStatus`/`reviewVerdict` are `null` for issues that stop at triage. Mint one `runId` per run, at the start of a new run (`telemetry.mjs run-id`); a resumed session reuses the original one (step 1). Records carry a `kind` discriminator — `"issue"` (the default; stamped when absent, so pre-existing logs stay valid) or `"retro"` (the step-6.5 pass record — a different shape, validated separately and excluded from every per-issue indicator; see `scripts/telemetry.mjs`).
- **`failureReason`** is `null` except alongside `implStatus: "error"` for a rate-limit death, where it's `"rate-limited"` (see step 5 and `references/escalation-policy.md`'s point-E recovery recipe) — a distinguishable marker `report()` uses to separate quota failures from model failures: `"rate-limited"` records are excluded from the model-quality indicators (first-pass yield, triage-miss, bounce rate) and tallied instead in the report's `quotaFailures` count (`renderReport()` prints a `quota failures:` line whenever it's non-zero), so a quota outage never makes those numbers look worse than the model actually performed. The engine's own stops, `"memory-critical"` and `"lease-wait"`, are the same kind of marker (beside `implStatus: "error"`, or `null` for a launch stop that never started), excluded from those indicators likewise and tallied in `resourceStops` (a `resource stops:` line).
- **`path`** records `"engine"` (primary — implement via the orchestrator, review from the skill), `"workflow"`, or `"inline"` (the two fallbacks). Effort is actuated literally on `engine` (implement sessions) and `workflow`; the `engine` path's review gate and the whole inline `Agent` fan-out are *nominal* (prompt-approximated — the `Agent` tool has no `effort` param), so the report never treats inline effort as actuated.
- **`tokens`** is `null` on the inline path (per-agent token counts aren't exposed to the orchestrator); on the engine path `ingest-wave` instead writes `cost.implement` (`{costUsd, input, output, cacheRead, cacheCreate, sessions, sessionIds}`) on each record that reached implement, summed from the ref's transcript over the sessions that wrote a result record and that no earlier record of the ref's run family lists, each session counted once. A session killed before writing one (a stall, a hard death) is not counted, so the cost can fall short of the real spend.
- **Ingest and audit:** `ingest-wave` and `audit` are specified in steps 6.3 and 7.
- **Escapes:** `node "$SD/scripts/telemetry.mjs" escapes [--now ISO]` reports the escaped-defect rate — merged PRs with a revert or a bug follow-up within 30 days — by merge month and `tuningVersion`, over PRs whose 30-day window has closed. It searches GitHub, so it is not run every wave. Each tally (`total`, `byMonth`, `byTuningVersion`) is `{prs, escaped, rate, strong, strongRate}`: `strong` counts PRs with at least one strong escape, a revert or a follow-up whose citation comes right after a closing keyword or after "regression from", "caused by" or "introduced in". A PR candidate closed without merging is not an escape; bug issues count whether open or closed; only the merged PR's own repo is searched.
- **Report:** `node "$SD/scripts/telemetry.mjs" report [--since ISO]` prints the indicators (JSON to stdout, table to stderr), broken down by complexity tier.
- **Storage:** append-only JSONL *outside* the repo — `$SHIP_DAG_TELEMETRY`, else `$XDG_STATE_HOME/ship-dag/runs.jsonl`, else `~/.local/state/ship-dag/runs.jsonl` — so collected run data can never be accidentally committed. `telemetry.mjs escapes` caches its GitHub answers beside it, in `$SHIP_DAG_ESCAPES_DIR`, else `$XDG_STATE_HOME/ship-dag/escapes`, else `~/.local/state/ship-dag/escapes`, under `v1/<owner>__<repo>/` (the repo dir lowercased): the candidate day files in `days-v3/` (each PR candidate stores its `state`), each merged PR's view as `pr-<n>.json`, and the one merged closing PR of a closed issue as `closing-<n>.json`. Nothing reads a `days-v2/` dir or a day file at the top level of a repo dir, and they can be deleted. Nothing is refreshed once cached: a settled day file keeps a candidate PR that was still open then as open, and a cached view stays as it was when someone edits a merged PR's title or linked issues. Deleting a file there makes escapes ask GitHub again; that is the remedy.
- **Tests:** `node --test 'scripts/**/*.test.mjs' 'eval/**/*.test.mjs'`, from the skill's root.

## Guardrails (non-negotiable)

- **Anonymity** — no Claude/Claude Code attribution in commits, PRs, issue comments, anywhere. Ghost-writer mode.
- **Worktree per issue** — created before any code; removed via `/cleanup` after merge.
- **CI before push** — local lint/format/typecheck/tests must pass before any push.
- **No auto-retry loops** — ≤2 manual retries on infra failure, then stop and report cost (rerunning after a `lease: no slot` denial is not an infra-failure retry; the two-denial give-up bounds it). The two-denial give-up applies to hook denials in engine sessions and subagents; the main agent's `run-ci-profile.mjs` exit 75 in step 6.2 is bounded instead by that step's 15-minute preflight and its 30-minute cap, which goes to point F whatever the pressure.
- **Data safety** — never reset/overwrite collected data; surgical changes only.
- **Never read a session transcript, and never measure with `/context`** — `<stateDir>/state/logs/issue-*.log` are full stream-json transcripts (megabytes); ask `scripts/diagnose-failure.mjs` instead. `/context` itself costs ~15k tokens a call, mostly the deferred-MCP inventory it lists but does not load, so two casual checks can outweigh a wave's actual overhead. To watch a run's context growth for free, sample `wc -c` on this session's transcript (`~/.claude/projects/<project>/<session-uuid>.jsonl`) at the interesting boundaries — launch, engine-done, pre-review, post-merge — and diff the byte counts.
- **Cross-repo cutover is a HITL gate** — never auto-release a wave whose readiness depends on a *different* repo's merge; confirm the upstream is published/deployed/consumable (or a gate command passed) first. "Satisfied" ≠ "merged" across a repo boundary (step 7, point C).
- **Wave sub-epics touch only themselves** — `wave-epic.mjs` creates, sweeps and closes only `ship-dag-wave` issues, re-parents only the epic's own children into one and a wave's open children back out, and never closes any other issue (`close` refuses a `--wave-epic` that isn't a `ship-dag-wave` sub-issue of `--epic`).
- **The retrospective proposes; it never disposes** — no ticket filed, edge written, spec edited, or issue closed without point-D approval, and it never touches merged code (step 6.5).
- **Auto-merge is a deliberate, requester-authorized deviation** from the house "never auto-merge" rule (`cross-repo-migration`). It is kept tightly behind the green gate (CI pass + no CONFIRMED blocking finding + no open questions), serialized in dependency order, and re-gated after any base-moving rebase. `--dry-run` and the six HITL points (A triage, B implement/review, C cross-repo cutover, D retrospective and tripwires, E rate-limit window, F resource pressure) are the escape hatches.
